# Датасет `НД_для_обучения`: как он устроен

Сводка по результатам разбора данных. Код и графики лежат в [notebooks/eda.ipynb](notebooks/eda.ipynb).

## TL;DR

- 100 исследований и 499 DICOM-файлов, но **уникальных снимков всего 252**. Остальные файлы — побайтовые дубликаты.
- В одном исследовании **не больше 3 уникальных снимков**, по одному на область: позвоночник, правое бедро, левое бедро.
- Разметка сделана **на исследование, отдельно по каждой области**. Метки области относятся к её снимку.
- В DICOM **нет** `BodyPartExamined`, `Laterality` и `PixelSpacing`. Область определяем эвристикой, она совпадает с разметкой в 98 из 100 исследований.
- **На снимках нет ROI, контуров и линий разметки**: только исходное изображение поля сканирования.
- Масштаб примерно **0.6 мм/px**. Точного значения в тегах нет.
- Нарушения есть в 48 (по сводке эксперта — в 50) исследованиях из 100. Классы маленькие: по ROI бедра всего 3–4 положительных примера.

## Структура файлов

```
НД_для_обучения/
├── разметка.xlsx
└── Исследования/
    └── <study_key>/                       # 100 папок, имя = ключ в разметка.xlsx
        └── series_00X_N_CR/               # всегда одна папка серии на исследование (кроме одного исключения)
            └── [A25xxxxxxx ]DXA/CR DXA/
                └── CR000000.dcm, CR000001.dcm, ...
```

- Имя папки исследования (`2.25.…` или `1.2.840.113619.…`) **не совпадает** с тегом `StudyInstanceUID` в файлах (`1.2.643.…`). Для связи с разметкой используем **имя папки**.
- Файлов в исследовании от 1 до 29.

## DICOM: что внутри

Одинаково во всех файлах:

| Тег | Значение |
|---|---|
| Modality | `CR` |
| Аппарат | GE Healthcare Lunar Prodigy Advance |
| SOP Class | Computed Radiography Image Storage |
| Пиксели | 8 бит, `MONOCHROME2`, 1 канал |
| Transfer Syntax | Implicit VR Little Endian (без сжатия) |
| Размер | 180–405 × 248–300 px (маленькие) |
| `BodyPartExamined`, `Laterality`, `ViewPosition`, `PixelSpacing` | **пусто или отсутствует** |
| Оверлеи (группа 6000), приватные теги | **нет** |

pydicom выдаёт warnings про невалидные UID (`1.2.643…`) и слишком длинные LO-поля. Читать файлы это не мешает.

### Значения полезных тегов

| Тег | Смысл | Особенности у нас |
|---|---|---|
| `StudyInstanceUID` | ID исследования | Анонимизирован, с именем папки не совпадает. Пишем в колонку `study_uid` результата. |
| `SOPInstanceUID` | ID файла | Уникален **даже у дубликатов**, поэтому дубликаты ищем по хешу пикселей. Пишем в колонку `image_uid`. |
| `InstanceNumber` | Номер снимка в серии | Нумерация с пропусками, подходит только для сортировки. |
| `SeriesNumber` | Номер серии | Совпадает с цифрой в имени папки, смысла не несёт. |
| `PatientOrientation` | Ориентация осей | `['L','F']`: вправо по снимку — к левому боку пациента, вниз — к ногам (стандартный AP-вид). |
| `ExposedArea` | Размер поля облучения | См. раздел «Масштаб». |
| `EntranceDoseInmGy` | Входная доза, мГр | 0.07–0.17 мГр. Для задачи, скорее всего, бесполезна. |

## Почему в исследовании много файлов

1. **Области съёмки.** В полном исследовании их три: позвоночник, правое бедро и левое бедро.
2. **Дубликаты.** Lunar выгружает одни и те же изображения несколько раз, например при переанализе или печати отчёта. У копий новые `SOPInstanceUID` и `InstanceNumber`, а пиксели идентичны.

После дедупликации по MD5 пикселей:

| Уникальных снимков | Исследований | Что в них |
|---|---|---|
| 3 | 74 | позвоночник, правое и левое бедро |
| 2 | 4 | позвоночник и одно бедро |
| 1 | 22 | только позвоночник |

Одинаковых снимков в **разных** исследованиях нет. Если делить выборку на train/val по исследованиям, утечки не будет.

**Правило для пайплайна:** сначала дедупликация по хешу пикселей внутри исследования, дальше работаем с уникальными снимками. В выходном CSV одна строка соответствует одному уникальному снимку (одной области).

## Определение области снимка

Тегов для этого нет, используем эвристику:

- **ширина 300 px → позвоночник**, 280 или 248 px → бедро;
- **сторона бедра**: верхняя треть снимка ярче со стороны головки бедра и таза. Ярче слева — **левое** бедро, ярче справа — **правое**.

Проверка: набор найденных областей совпадает с набором размеченных в **98 из 100** исследований. В двух расхождениях есть эндопротез тазобедренного сустава, и эксперт это бедро не размечал.

Функция `guess_region` есть в ноутбуке. Для продакшена её лучше заменить маленьким классификатором или хотя бы подстраховать им.

## Масштаб (мм/px)

`PixelSpacing` отсутствует. `ExposedArea`, судя по всему, содержит размер поля сканирования в мм (ширина × длина):

- у **175 из 239** снимков с ненулевым значением отношение `ExposedArea / размер в px` ≈ **0.6 мм/px** по обеим осям. Например, [170, 160] соответствует снимку 263×280 px;
- у **64** снимков первое значение 520, соотношение ≈ 1.8. Это другая единица или режим, причина неясна;
- у **13** снимков значение `[0, 0]`;
- тег **не привязан к пикселям жёстко**: у побайтово одинаковых снимков бывают разные значения.

**Вывод:** на `ExposedArea` не полагаемся и принимаем фиксированный масштаб ≈ 0.6 мм/px (поле 17–18 см по ширине). Это нужно для критерия ROI бедра, где отступы заданы в сантиметрах (3 см ≈ 50 px, 2 см ≈ 33 px). Гипотезу ещё стоит проверить по анатомии (высота L3 около 25–30 мм, то есть примерно 45 px).

## Разметка (`разметка.xlsx`)

Заголовок занимает **две строки** с объединёнными ячейками, поэтому читаем с `header=None` и задаём имена колонок сами:

| Колонка xlsx | Имя у нас | Смысл (1 = нарушение) |
|---|---|---|
| A | `n` | порядковый номер |
| B | `study` | ключ = имя папки |
| C | `spine_position` | позвоночник: некорректная укладка (не видны Th12 или гребни подвздошных костей) |
| D | `spine_axis` | позвоночник: наклон оси больше 5° |
| E | `spine_artifacts` | позвоночник: посторонние предметы или артефакты |
| F | `rhip_rotation` | правое бедро: позиционирование/ротация (малый вертел) |
| G | `rhip_roi` | правое бедро: некорректная область интереса (запас меньше 3 см сверху и снизу или меньше 2 см сбоку) |
| H | `lhip_rotation` | левое бедро: позиционирование/ротация |
| I | `lhip_roi` | левое бедро: область интереса |
| J–L | `spine_bad`, `rhip_bad`, `lhip_bad` | итог по области |
| M | `comment` | комментарий эксперта |
| N–S | — | сводка эксперта (50 норма / 50 патология), не используем |

NaN в колонках бедра означает, что снимка этой области в исследовании нет (или бедро с эндопротезом).

Код загрузки:

```python
lab = pd.read_excel('НД_для_обучения/разметка.xlsx', header=None).iloc[2:, :13]
lab.columns = ['n', 'study', 'spine_position', 'spine_axis', 'spine_artifacts',
               'rhip_rotation', 'rhip_roi', 'lhip_rotation', 'lhip_roi',
               'spine_bad', 'rhip_bad', 'lhip_bad', 'comment']
```

### Комментарии экспертов
`сколиоз` (13), `Требует внимание` (2), `L6, люмбализация`, `Сколиоз, не верная разметка`, `перелом`, `эндопротезирования ТБС` (2), `Отклонение оси, нет малых вертелов`, `Хороший пример ротации`, `Хороший пример отклонения оси`.

Сколиоз, люмбализация, перелом и эндопротез — клинические особенности, а не ошибки укладки. Решение о том, как с ними обращаться (отдельный класс, исключить или «требует внимания»), команде ещё предстоит принять.

## Про «корректность разметки»

В ТЗ упоминается проверка разметки анатомических структур (например, как проведены межпозвонковые линии). **По этим данным её проверить нельзя**: ROI, линий и оверлеев нет ни в пикселях, ни в тегах. Все 7 критериев из xlsx оцениваются по самому изображению. «Корректность области интересов» у бедра означает достаточный запас поля сканирования вокруг бедра, а не нарисованные оператором линии.

**Открытый вопрос к организаторам:** будут ли в тестовых данных снимки с наложенной разметкой или отчёты Lunar. Стоит также свериться с методическими рекомендациями, разделы 2.6 и 2.7.

## Выводы для моделирования

- Дедупликация обязательна, иначе будет утечка и завышенные метрики.
- Делим выборку **по исследованиям** (group split), стратифицируя по наличию нарушения.
- Данных очень мало (99 снимков позвоночника, 151 снимок бедра), поэтому смотрим в сторону предобученных бэкбонов, аугментаций, кросс-валидации, а также геометрических и эвристических подходов (ось позвоночника, границы поля, малый вертел).
- Для `*_roi` положительных примеров 3–4 на сторону. Здесь, скорее всего, нужна геометрическая проверка, а не классификатор.
- Метрики считаем с 95% доверительными интервалами: бутстрэп по исследованиям для F1 и AUC, интервал Уилсона для чувствительности и специфичности. Прогонять модель несколько раз для этого не нужно. На такой выборке интервалы получатся широкими.
