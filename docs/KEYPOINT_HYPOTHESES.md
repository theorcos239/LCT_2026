# Как получать и оценивать варианты разметки точек

Рабочий `Predictor` теперь использует первый этап этого подхода для полностью
видимых L1–L4: до шести пиков каждой из четырёх карт центров, 21 отклик в
каждом кандидате, геометрию и поддержку пяти дисков. Из лучших цепочек
выбирается одна; softmax даёт **относительный вес лидера**, но по умолчанию
координаты разных цепочек не смешиваются. При частичной видимости остаётся
прежний декодер. Ниже описан также более широкий исследовательский план:
полные варианты для всех 21 точки пока не встроены.

1. **Найти кандидатов.** На каждом снимке взять несколько локальных пиков каждой
   из 21 карт точек позвоночника. Близкие пики разных карт объединить в одну
   кандидатную позицию. Сохранить исходную карту каждого пика и её высоту.
   Вариант «точка не найдена» оставить допустимым, когда её нет в кадре.
2. **Посмотреть все карты в каждом кандидате.** Для *каждого* кандидата `p`
   записать **21 число**: отклик каждой карты позвоночника `H_name(p)`, даже
   если кандидат исходно найден на другой карте. Получится таблица
   «кандидатная позиция × 21 карта»: например, один кандидат может
   поддерживаться картами `l3_center` и `l4_center` с разной силой. Это
   21 оценка для кандидата, но пока не 21 вероятность того, «кем он является»:
   карты центра, края и диска описывают разные структуры и не образуют
   взаимоисключающие классы.
3. **Собрать несколько вариантов.** Сначала выбрать несколько цепочек центров
   L1–L4: сверху вниз, без повторного использования одной позиции, с разумными
   расстояниями и направлением между соседями. Для каждой цепочки подобрать
   кандидатов краёв, дисков, Th12 и подвздошных гребней в соответствующих
   областях. Сохранять несколько лучших полных вариантов, а не только первый.
   Перебирать все комбинации 21 карты сразу не требуется.
4. **Оценить каждый вариант.** Сложить логарифмы откликов *назначенных* карт
   в выбранных позициях и вычесть штрафы за нарушение геометрии:

   `score(H) = Σ log(H_name(p_name) + ε) − штрафы_геометрии`.

   Сравнивать варианты с одинаковым набором видимых точек; отсутствие точки
   учитывать отдельным баллом, иначе вариантам с меньшим числом точек будет
   проще получить высокий счёт. Сдвиг всей ровной цепочки геометрия может не
   различить: здесь важны отклики карт Th12 и дисков.
5. **Проверить влияние на результат.** Посчитать итоговый угол и вердикт для
   нескольких лучших вариантов. Если они совпадают, неоднозначность номеров
   практически не влияет на решение. Если различаются и один вариант нельзя
   уверенно выбрать, пометить измерение по точкам как сомнительное и сверить
   с уже существующим контурным расчётом оси. Контур сам по себе не определяет
   номера позвонков.

`softmax(score / T)` может дать **относительные веса рассмотренных вариантов**.
Это ещё не вероятность правильной разметки: температуру `T`, пороги отсева и
частоту ошибок нужно проверить на OOF-разметке. Сначала полезно измерить,
попадает ли правильный вариант хотя бы в несколько лучших.

**Что встроено:** `src/dxa_qc/structure.py:chain_decode_hypotheses` возвращает
координаты и диагностику `top1_relative_weight`, `score_gap_top2` и число
рассмотренных гипотез. `infer.spine_chain_mode: hypotheses` выбирает его;
`legacy` оставляет прежний декодер. Опция `spine_chain_average: true` включает
экспериментальное softmax-усреднение координат пяти цепочек. По умолчанию она
выключена: усреднение разных уровней может поставить точку между позвонками.
Полные варианты всех 21 точек и их веса в сервис пока не встроены.

## Как проверить идею на настоящих предсказаниях

Исследовательский скрипт `tools/evaluate_trajectory_hypotheses.py` делает
именно такой отбор: собирает пики всех 21 карт, для каждого кандидата читает
все 21 отклик, оставляет несколько цепочек центров и оценивает каждую вместе
с дисками, краями, Th12 и гребнями. Это **первая версия алгоритма**; её пороги
и штрафы не подобраны по данным.

Для честного теста нужны карты, полученные моделью каждого фолда **только на
его отложенных снимках**. Если есть `data/keypoints.npz` и веса
`runs/keypoints/fold0.pt`, `fold1.pt`, их можно сохранить и оценить:

```bash
PYTHONPATH=src python tools/export_oof_heatmaps.py \
  --run runs/keypoints --pack data/keypoints.npz \
  --out Processing/oof_heatmaps.npz
PYTHONPATH=src python tools/evaluate_trajectory_hypotheses.py \
  --heatmaps Processing/oof_heatmaps.npz \
  --oof runs/keypoints/oof.npz \
  --out Processing/trajectory_hypotheses.csv
```

Сравнивать с нынешней расшифровкой: сколько снимков имеют верные уровни
L1–L4, ошибку угла оси, сколько раз правильная цепочка есть хотя бы в топ-5,
а также число пиков и разницу оценок двух лучших вариантов. Топ-5 — проверка
того, **содержат ли карты нужную альтернативу**; это ещё не рабочая точность.
Для итогового решения надо оценивать лучший вариант без знания разметки.

В репозитории есть `runs/keypoints/oof.npz` с выбранными координатами и
высотами главных пиков, но без самих карт. Исходный `data/keypoints.npz`
восстановлен локально из истории Git. Веса `Processing/drive_models/fold0.pt`
и `fold1.pt` получены
из папки команды, однако относятся к **другому прогону**, чем локальный OOF:
медиана в скачанном `fold0.pt` — 2.72 мм, а в локальном OOF фолда 0 — 1.32 мм.
Карты по этим весам можно изучать, но их результаты нельзя приписывать
текущему прогону без соответствующих чекпоинтов.

## Быстрая проверка на весах из Drive (фолды 0 и 1)

`tools/evaluate_softmax_chains.py` воспроизводимо прогоняет 37 отложенных
снимков позвоночника. Для центров L1–L4 он объединяет до шести пиков каждой
карты, читает в каждой кандидатной позиции отклики всех 21 карт, перебирает
упорядоченные цепочки и штрафует неровный шаг. Варианты с дисками дополнительно
проверяют, лежат ли их пики на ожидаемых уровнях. Критерий верного уровня —
ближайший размеченный центр, как в `evaluate.py`; Th12 и L5 на краях цепочки
частично оцениваются геометрически. Вес геометрии 10 взят из существующего
декодера, вес дисков 0.5 и температура softmax 1 заданы до теста. Это
исследовательская оценка, параметры не подбирались на независимом наборе.

| Выбор L1–L4 | Верны все 4 уровня | Верных центров |
| --- | ---: | ---: |
| Главный пик каждой карты | 5/37 | 78/148 |
| Встроенный декодер гипотез (все четыре центра принудительно активны) | 24/37 | 113/148 |
| Перебор + геометрия, сырые отклики | 22/37 | 104/148 |
| То же, отклики нормированы по 21 карте | 23/37 | 112/148 |
| Перебор + геометрия + диски | 24/37 | 116/148 |
| То же с нормировкой по 21 карте | 24/37 | 114/148 |
| Softmax-среднее пяти цепочек при учёте дисков | 25/37 | — |

У существующего `chain_decode` на этих же картах и сохранённых порогах
видимости — 5/37: на 36/37 кадров он не меняет центры, так как пороги
подавляют слабые карты. Если принудительно считать все четыре центра видимыми
и снизить порог поиска пика до 0.001, существующий декодер даёт 24/37. Поэтому
основной выигрыш здесь объясняют кандидаты и работа цепочки; **softmax сам по
себе не доказал улучшения сверх уже существующей геометрии**. Он сохраняет
порядок гипотез при выборе максимума и может быть полезен для оценки
неуверенности. Верная цепочка входит в первые пять вариантов на 25–27 кадрах,
в зависимости от балла. Проверка на весах текущего локального OOF пока
невозможна: соответствующих чекпоинтов нет.

В локальном OOF текущего прогона все четыре центра проходят сохранённые пороги
на 34 из 37 снимков позвоночника. Это говорит лишь о том, что новый декодер
смог бы включиться на большинстве этих снимков при наличии соответствующих
весов; величина улучшения на них ещё неизвестна.

Повторить эксперимент:

```bash
PYTHONPATH=src Processing/.venv-keypoints/bin/python \
  tools/evaluate_softmax_chains.py --run Processing/drive_models --device mps
```

Построчный результат сохраняется в игнорируемый файл
`Processing/drive_models/softmax_chain_eval.csv`.
