# Готовность к финальным шагам: фронтенд

Дата: 2026-09-25. Проверка сделана по фактическому состоянию репозитория
(коммит `261b41f`), а не по документации: прогнаны тесты, поднято API в
процессе, разобран текст ТЗ (`4. ДепЗдрав.pdf`).

- `python -m service.test_service` → **24 пройдено, 0 провалено** (формат

- Рабочее дерево чистое, последний коммит `261b41f`.

Все **обязательные** пункты ТЗ закрыты: контейнеризация (§3.2), API
пакетной обработки (§3.2), xlsx/csv ровно с колонками §2.5, скрипты сборки
и запуска на POSIX sh, обработка ошибок без утечки исключений (§2.7),
воспроизводимость (§2.7), 0.08 с на исследование при лимите в 3 минуты.

## 2. Фронтенд — не самый приоритетный из оставшихся шагов

Текст ТЗ, §2.6 «Дополнительный функционал»:

> Дополнительная серия с визуализацией… Текстовое описание в формате
> DICOM SR. Автоматическая коррекция разметки с подтверждением
> специалистом. **Интерактивный веб-интерфейс** для загрузки, просмотра и
> пакетной обработки.

Веб-интерфейс — **бонус**, а не обязательство. При этом обязательными к
финальной сдаче (§4, §7.2) остаются вещи, которых в репозитории пока нет:

| что | статус на 2026-09-25 | статус на 2026-09-27 | вес |
|---|---|---|---|
| **Презентация и демо-сценарий** (§4, §7.2) | отсутствует | отсутствует | обязательно, отдельный критерий 8.5 |
| Руководство пользователя, по развёртыванию, описание обучения (§5) | частично, внутри README | **готово**: `docs/USER_GUIDE.md`, `DEPLOYMENT.md`, `TRAINING.md` | обязательно «дополнительно» |
| Дайджест базового образа в `Dockerfile` | не проставлен | **готово**, плюс `requirements.lock` с транзитивными зависимостями | §3.2 |
| Веб-интерфейс (§2.6) | отсутствует | отсутствует | бонус |
| DICOM SR (§2.6) | отсутствует | **готово**: `--sr`, `POST /analyze/sr`, `/jobs/{id}/sr` | бонус |
| Модель ключевых точек | код есть, весов нет | обучена, подключается флагом `--keypoints`, по умолчанию выключена (README) | главный резерв качества (ротация OOF AUC 0.69) |

Статус на 2026-09-27 — после доработок по критериям ТЗ без фронтенда и
презентации; полный список изменений — в истории ветки
`report/frontend-readiness`.

Фронт стоит делать — это единственный из этого списка артефакт, который
судья потрогает руками на питче. Но если выбирать один приоритет —
презентация обязательна, а интерфейс нет.

## 3. Техническая готовность под фронт

Готово всё, что нужно UI:

- `/analyze` возвращает не только вердикт, но и `details` со всеми
  измерениями (углы, мм, мм²), `flags`, русские описания.
- `/analyze/overlay` — PNG с разметкой вердикта по любому кадру.
- `/batch` + `/jobs/{id}` отдают `progress: "12/252"` и `summary` — живой
  прогресс-бар делается без доработок бэка.

Три вещи в бэке придётся тронуть (суммарно ~час):

1. **CORS не включён.** Страница с другого origin получит отказ.
   Правильное решение — не добавлять `CORSMiddleware`, а раздавать UI из
   самого FastAPI (`StaticFiles` + HTML на `/`): один origin, один
   контейнер, и заявление README «ни один эндпоинт не ходит в сеть»
   остаётся верным.
2. **Оверлеи пачки недоступны поштучно.** В `service/api.py`
   (`_run_job`) в `finally` вызывается `shutil.rmtree(data_dir)` — после
   задания пиксели удалены, перерисовать кадр нельзя. Нужен
   `GET /jobs/{id}/overlays/{name}.png`, читающий запись из уже собранного
   zip (~15 строк).
3. **Оверлеи пишутся только для кадров с нарушением**
   (`service/report.py`, `write_overlays`). Для демо «вот качественный
   снимок, вот почему он качественный» этого не хватает — либо флаг «все
   кадры», либо показывать чистые кадры через `/analyze/overlay`.

Дополнительно: `JOBS` — словарь в памяти, задания не переживают рестарт,
у `JOBS_DIR` нет TTL. Для демо нормально, в README стоит оговорить.

## 4. Варианты фронтенда

| вариант | трудозатраты | соответствие ТЗ | риск | что даёт на защите |
|---|---|---|---|---|
| **Одностраничный HTML внутри FastAPI** | 4–8 ч | §2.6 дословно | низкий | **высокое** |
| SPA на React/Vite | 1.5–2 дня | то же самое | средний | то же самое |
| Gradio / Streamlit | 1–2 ч | §2.6 формально | низкий | среднее |
| Telegram-бот | 3–5 ч | **нарушает §3.2** | высокий | отрицательное |
| Desktop (PyQt/Tauri) | 2–3 дня | мимо §3.2 | высокий | низкое |
| OHIF / Orthanc-вьюер | 3–5 дней | сверх ТЗ | очень высокий | высокое, но не успеть |

**1. Одностраничный HTML, встроенный в сервис — рекомендуется.**
Один файл, без сборки, отдаётся с `/`. У команды уже есть этот паттерн —
`Processing/razmetka_all.html` на 6.8 МБ с canvas, тёмной темой и
клавиатурной навигацией, написанный для разметки. Стиль и приёмы
переиспользуются, риск почти нулевой. Сценарий: drag-drop zip → прогресс
`done/total` → таблица с фильтром по области и типу нарушения → клик по
строке → оверлей рядом с числами («ось 6.6°», «отступ 21 мм при норме
30») и флагами → кнопки xlsx / details.json / overlays.zip. Образ не
растёт, вторая точка отказа не появляется.

**2. SPA на React/Vite — не окупается.**
Даёт то же самое, что вариант 1, но добавляет node-стадию в Dockerfile,
вторую точку отказа при сборке и полдня времени. Оправдано только если в
команде есть свободный фронтендер.

**3. Gradio / Streamlit — запасной вариант при нехватке времени.**
Час работы, но +200–400 МБ к образу, которым README отдельно гордится
(«450 МБ вместо 2.5 ГБ»), плюс генеричный вид. У Streamlit конкретная
поломка: он перезапускает скрипт на каждое действие, и модель фоновых
заданий с `JOBS` в памяти разваливается. Gradio в этом смысле безопаснее.

**4. Telegram-бот — не делать.**
§3.2: решение должно запускаться «без обращения к внешним закрытым
сервисам и без передачи медицинских изображений во внешние системы». Бот
отправляет пиксели DXA на серверы Telegram — прямое нарушение, даже на
обезличенных данных, и противоречит строчке README «изображения за
пределы контейнера не уходят». На критерии 8.3 («пригодность для
локального использования») это минус. В презентацию как канал
уведомлений в закрытом контуре — можно, кодом — нет.

**5. Desktop-приложение — мимо задачи.**
Судьи запускают Linux-контейнер по `run.sh`; десктоп-сборка под
Windows/macOS — артефакт, которого никто не просил, 2–3 дня упаковки.

**6. Вьюер поверх Orthanc + OHIF — на слайд, не в код.**
Максимальная клиническая достоверность, прямое попадание в критерий 8.5
(«реалистичность плана пилотирования и внедрения»), но это отдельный
проект. Одного слайда «так это встраивается в PACS» достаточно.

## 5. Рекомендация

Вариант 1, один рабочий день, и в него же вытащить ещё один бонус §2.6
почти бесплатно: «автоматическая коррекция разметки с подтверждением
специалистом». Полноценная коррекция упирается в необученную модель
точек, но экран «вердикт + оверлей + кнопки Подтвердить / Отклонить,
решение оператора уходит в отчёт» — это human-in-the-loop, который
закрывается той же страницей и хорошо звучит на питче. Итого одна
страница закрывает два пункта из четырёх бонусных.

Порядок работ: дайджест образа (30 сек) → эндпоинт оверлея по имени →
страница → презентация.
