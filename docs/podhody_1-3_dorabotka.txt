================================================================================
  Подходы 1–3 к доработке алгоритма DXA QC
  Сервис контроля качества денситометрических исследований (ЛЦТ 2026)
================================================================================

Документ расшифровывает три приоритетных направления улучшения алгоритма
относительно текущего решения (геометрия + cnn_qc, честная OOF-оценка:
F1 0.58, ROC-AUC 0.78 по классу «есть нарушение»).

Опора: ТЗ «4. ДепЗдрав.pdf» (§2.3 — пять критериев; §8.4 — F1 и ROC-AUC),
README.md, DATASET.md, docs/KEYPOINTS.md, cnn_qc/README.md, hip_rotation/,
spine_qc/.


--------------------------------------------------------------------------------
Общая рамка (для всех трёх подходов)
--------------------------------------------------------------------------------

Что требует ТЗ:
  • пять критериев: spine_position, spine_axis, spine_artifacts,
    hip_rotation, hip_roi;
  • сырой DICOM без разметки оператора;
  • отчёт (xlsx/csv), класс качества + типы нарушений;
  • ≤ 3 минуты на исследование, локально, без передачи снимков наружу;
  • метрики: F1 и ROC-AUC (желательно с 95% ДИ), в т.ч. по типам нарушений.

Что нельзя ломать без нужды:
  • объяснимость в мм и градусах (геометрия остаётся в details/оверлее);
  • детерминизм и один поток onnxruntime/BLAS;
  • честную оценку только out-of-fold по folds.csv (группа = исследование).

Текущие узкие места (honest OOF):
  • hip_rotation     F1 0.55 / AUC 0.82   — главный вклад в общий F1;
  • spine_axis       F1 0.25 / AUC 0.82   — ложные срабатывания на сколиозе;
  • spine_position   F1 0.32 / AUC 0.82   — всего 6 позитивов; Th12 не проверяется;
  • hip_roi          F1 0.71 (правило длины поля) — эталон ≠ буквальный рис. 6.


================================================================================
ПОДХОД 1. Дожать ключевые точки (низкий риск)
================================================================================

1.1. Суть одной фразой
----------------------
Дообучить модель ключевых точек на оставшихся фолдах, включить её в вердикт
там, где сквозная ошибка уже мала (ось, ROI), и использовать видимость
точек для укладки (гребни, Th12) — закрывая пробел ТЗ по верхней границе
кадра позвоночника.


1.2. Что уже есть в коде
------------------------
Пакет:          src/dxa_qc/
Конфиг:         configs/keypoints.yaml
Прогон/метрики: runs/keypoints/
Включение:      --keypoints у CLI, DXA_QC_KEYPOINTS=1 у API
Мост в сервис:  service/keypoints_backend.py

Архитектура: U-Net, энкодер ResNet-34, 29 каналов (21 точка позвоночника,
8 — бедро). Размечено 242 кадра из 252.

В поставке обучены только фолды 0 и 1 из пяти. Метрики ниже — out-of-fold
на ~40% набора (фолды 0–1). Фолды 2–4 не обучались.

Сквозная ошибка «точки модели → величина критерия» (OOF, фолды 0–1):

  величина              медиана    p90      порог ТЗ / разрыв    вердикт сейчас
  угол оси              0.50°      1.41°    5°                   можно брать
  ROI сверху/снизу/бок  ~0.5 мм    ~1.5 мм  30 / 30 / 20 мм      можно брать
  выступ малого вертела 0.75 мм    2.18 мм  разрыв классов ~2.1  НЕ брать

Ротация по точкам не улучшается: ошибка выступа сопоставима с разрывом
классов. Укладка по видимости iliac_* формально осмысленна (после правок
модель меньше «выдумывает» точки), но на 6 позитивах эталона переводить
вердикт целиком нельзя — сначала диагностика, потом осторожный свод.


1.3. Зачем это нужно по ТЗ
--------------------------
Критерий spine_position (ТЗ §2.3, рис. 1):
  • внизу видны верхние края подвздошных костей;
  • сверху — половина тела Th12.

Сейчас сервис проверяет в основном нижнюю часть (доля кости в зонах гребней,
iliac_area). Верхняя граница (Th12) в вердикт не входит: разметки уровня
в эталоне xlsx нет, проверять правило было не на чем. У модели точек есть
каналы th12_top / th12_bottom и калиброванный порог видимости — это прямой
способ закрыть пункт ТЗ без новой архитектуры.


1.4. Что сделать по шагам
-------------------------
Шаг A. Дообучение фолдов 2–4
  PYTHONPATH=src python -m dxa_qc.train --config configs/keypoints.yaml
  (готовые фолды пропускаются)
  Нужны: torch (requirements-train.txt), data/keypoints.npz, локальный
  набор НД_для_обучения/ (в git не входит).

Шаг B. Полный OOF-прогон и сравнение с контуром
  python -m dxa_qc.evaluate --run runs/keypoints
  python -m service.evaluate --keypoints --out runs/metrics_keypoints.json
  Смотреть: macro-F1, F1/AUC по spine_axis, hip_roi, spine_position;
  время на кадр (сейчас keypoints ~12× медленнее контура: ~347 мс vs ~28 мс).

Шаг C. Политика вердикта (не менять без метрик)
  • ось: угол по точкам вместо (или в своде с) контуром; при расхождении
    > 2° — флаг keypoints:axis_methods_disagree (уже заложена идея в pipeline);
  • ROI: отступы по точкам; при расхождении > 5 мм — флаг;
  • укладка: видимость iliac_left/right и th12_top как признаки;
    бинарь — только после вложенной калибровки на всех 5 фолдах;
    пока мало позитивов — писать в details и/или мягко влиять на
    quality_probability, не ломая порог iliac_area вслепую;
  • ротация: по-прежнему hip_rotation (+ cnn_qc); выступ по точкам —
    только диагностика в details.

Шаг D. Поставка
  • по умолчанию можно оставить выключенным, если лимит образа/времени критичен
    (torch + веса заметно раздувают образ; есть Dockerfile.keypoints);
  • либо включить по умолчанию, если OOF на 5 фолдах подтвердит выигрыш
    и p95 времени останется << 3 мин (сейчас запас огромный: ~1.6 с/исследование).


1.5. Плюсы и минусы
-------------------
Плюсы:
  • инфраструктура, разметка и мост в сервис уже есть;
  • закрывает Th12 — явный пробел относительно рис. 1 ТЗ;
  • по оси на части данных уже было F1 0.50 vs 0.33 у контура (мало
    нарушений оси на фолдах 0–1 — перепроверить на полном OOF);
  • низкий архитектурный риск: геометрия остаётся fallback.

Минусы:
  • нужно дообучить 3 фолда (время GPU/CPU);
  • torch в рантайме или отдельный образ;
  • ротацию не лечит;
  • укладка упирается в 6 меток эталона — потолок F1 может остаться низким
    даже при хорошем AUC видимости;
  • p90 ошибок по позвонкам всё ещё большой из-за сдвигов нумерации
    (numbering_doubt) — для угла оси это частично сглаживается, для Th12
    видимость важнее точной координаты.


1.6. Критерий успеха
--------------------
  • обучены фолды 0–4, честный OOF на всём размеченном наборе;
  • spine_axis и/или hip_roi: F1 или AUC не хуже контура, лучше — выше;
  • появляется проверяемый сигнал по Th12 (хотя бы в details + флаг);
  • сервис с --keypoints не падает без весов (флаг keypoints:unavailable);
  • время на исследование остаётся порядка секунд, не минут.


1.7. Связанные файлы
--------------------
  src/dxa_qc/train.py, infer.py, structure.py, evaluate.py
  service/keypoints_backend.py, service/pipeline.py
  docs/KEYPOINTS.md, configs/keypoints.yaml, runs/keypoints/


================================================================================
ПОДХОД 2. Сколиоз ≠ наклон оси (средний риск, высокий выигрыш по F1)
================================================================================

2.1. Суть одной фразой
----------------------
Не считать нарушением оси каждый кадр с углом выше порога: отделить
«наклон всего поясничного отдела» (нарушение по ТЗ/эксперту) от
«S-образного изгиба / сколиоза», который эксперт нарушением оси не метит.


2.2. Почему это главный тормоз spine_axis
-----------------------------------------
Текущие OOF-метрики оси: чувствительность 0.30, специфичность 0.88,
F1 0.25 при ROC-AUC измерения 0.82.

То есть угол хорошо ранжирует, а бинарный вердикт плохой.

Разбор эталона (DATASET.md):
  • у всех 14 исследований с комментарием про сколиоз spine_axis = 0
    в разметке эксперта;
  • при этом угол по центрам тел доходит до 8.8°;
  • у 6 из 14 угол выше порога решения сервиса 4.0°;
  • у 5 из 14 — выше 5° из ТЗ.

Именно эти кадры — главный источник лишних срабатываний (false positive)
по оси. Сверточная сеть «на ось» дала ROC-AUC ~0.51 — сигнала «сколиоз
vs наклон» в полном кадре нет. Флаг axis:curved (изгиб трека > 12 мм)
уже считается в spine_qc, но в вердикт не входит — только подсказка.


2.3. Что считает геометрия сейчас
---------------------------------
spine_qc/criteria.py, функция axis:
  • оценка A: прямая Тейла–Сена по центрам тел позвонков, угол к вертикали;
  • оценка B: угол по боковым краям колонны;
  • порог решения ~4.0° (не 5° ТЗ: измеритель читает примерно на градус ниже);
  • при |A − B| > 2° → флаг axis:estimates_disagree;
  • при изгибе трека > 12 мм → флаг axis:curved;
  • вердикт = сравнение угла с порогом (геометрия), без учёта curved.

Порог 4° и две конструкции угла трогать не обязательно: проблема не в
измерении угла, а в правиле «угол > порога ⇒ нарушение» на сколиотических
кадрах.


2.4. Варианты реализации (от простого к сложному)
-------------------------------------------------

Вариант 2A. Жёсткое правило (быстрый эксперимент)
  Ставить spine_axis только если:
      angle_deg > axis_threshold
      AND curvature_mm <= curved_threshold   (или AND не axis:curved)
  Калибровка curved_threshold — вложенный OOF по folds.csv:
  перебор порога изгиба, максимизация F1 / балансировка FP на 14 сколиозах
  и FN на истинных наклонах.
  Риск: изгиб 5–13 мм бывает и у кадров без сколиоза в комментарии
  (у 54 из 75 «не-ось» изгиб тоже ≥ 5 мм) — один порог 12 мм может
  быть груб; нужен sweep, не фиксировать число «с потолка».

Вариант 2B. Признаки + логистическая регрессия
  Признаки на кадр (всё уже почти есть в measurements):
    • angle_centers_deg, angle_edges_deg, |разница|;
    • curvature_mm (макс. отклонение трека от прямой);
    • знак/асимметрия кривизны верх vs низ (две половины трека);
    • опционально: длина дуги / хорды, число перемен знака отклонения.
  Цель: P(экспертная метка spine_axis=1).
  Обучение: OOF по исследованиям; в вердикт — порог на вероятности
  (вложенно), угол по-прежнему в отчёте в градусах.
  Плюс: объяснимость сохраняется; «сколиоз» становится частью модели,
  а не одним if.

Вариант 2C. Мягкий режим (если эталон закрытого набора неизвестен)
  При axis:curved:
    • не снимать нарушение полностью, а
    • снизить вклад в quality_probability / поставить confidence=low;
    • в violation_description явно писать «возможен сколиоз, проверьте».
  Меньше риск просадить recall на закрытом наборе, если там сколиоз
  вдруг считают нарушением оси.


2.5. Чего делать не стоит
-------------------------
  • учить CNN заново «на ось» без новых признаков — уже AUC 0.51;
  • править эталон xlsx (сколиоз → 1) — эталон не трогаем, расхождения
    документируем;
  • поднимать порог угла до 8–9°, чтобы «проглотить» сколиоз — убьёт
    чувствительность на истинных наклонах 5–7°.


2.6. Плюсы и минусы
-------------------
Плюсы:
  • бьёт точно в измеренную причину F1 0.25;
  • без GPU, без новых весов, минуты на калибровку;
  • угол в мм/° остаётся в отчёте — оператор видит число;
  • высокий ожидаемый вклад в macro-F1 при малой трудоёмкости.

Минусы:
  • на закрытом наборе политика эксперта по сколиозу может отличаться;
  • изгиб как единственный признак перекрывается с нормой (см. DATASET);
  • мало истинных нарушений оси (~10) — любой порог шумный, только OOF.


2.7. Критерий успеха
--------------------
  • honest OOF F1 по spine_axis заметно выше 0.25 (ориентир — хотя бы
    уровень «не хуже случайного баланса», реалистично 0.35–0.50);
  • число FP на кадрах с комментарием «сколиоз» падает;
  • recall по истинным spine_axis=1 не проседает катастрофически
    (следить во вложенной таблице ошибок);
  • флаг axis:curved и угол по-прежнему видны в details/flags.


2.8. Связанные файлы
--------------------
  spine_qc/criteria.py      — axis(), curvature, flags
  spine_qc/calibrate.py     — --sweep, подбор порогов
  spine_qc/thresholds.json
  spine_qc/measurements.csv
  service/pipeline.py       — сбор violations
  DATASET.md                — раздел про сколиоз и ось


================================================================================
ПОДХОД 3. Ротация: локальный кроп + мультизадача (высокий потенциал)
================================================================================

3.1. Суть одной фразой
----------------------
Не пытаться точнее измерить выступ малого вертела субпиксельно (сигнал
~2 мм, ошибки того же порядка), а сменить постановку для сети: смотреть
крупный план вертельной зоны (как врач на рис. 5 ТЗ) и учить различать
три состояния — норма / переротация / недоротация — с аккуратной
калибровкой порога бинарного вердикта.


3.2. Как работает сейчас
------------------------
Цепочка (service/pipeline.py):
  1) hip_roi/kit2 → верхушка большого вертела T;
  2) hip_rotation.detect → площадь выступа (мм²), corridor_distance
     за коридором нормы ~96–272 мм²;
  3) cnn_qc.assess('rotation') на ВСЁМ кадре (длинная сторона → 320 px);
  4) свод: p = σ(a·logit(p_cnn) + b·geometry + c) → hip_rotation да/нет.

Честные цифры:
  геометрия (выступ)     AUC 0.68   F1 0.48
  CNN, полный кадр       AUC 0.80
  свод                   AUC 0.82   F1 0.55

Вывод: ранжирование уже неплохое; F1 упирается в порог и в то, что
два разных механизма (нет вертела / слишком большой вертел) схлопнуты
в одну бинарную метку и один corridor_distance.


3.3. Почему геометрия и keypoints не спасают ротацию
----------------------------------------------------
  • разрыв классов по выступу ~2 мм при ширине диафиза ~35 мм;
  • выступ = разность координат → ошибки складываются;
  • «вид кадра» 64–128 px: AUC 0.50 (вертел пропадает);
  • признаки по keypoints (шейка, NSA, …): AUC ≤ 0.66;
  • ошибка выступа по точкам 0.75 мм (p90 2.2) ≈ разрыв классов.

Значит, нужен другой взгляд: больше пикселей на мм в зоне вертела и
явная трёхклассовая семантика рис. 5.


3.4. Локальный кроп
-------------------
Якоря (уже есть, стабильнее самого малого вертела):
  • T — верхушка большого вертела (kit2);
  • медиальный/латеральный профиль кости (hip_roi.geometry);
  • сторона lh/rh; rh отражается в lh, как в cnn_qc сейчас.

Ориентировочное окно (фиксировать в мм заранее, не подгонять по F1):
  сверху:  T − 10…15 мм
  снизу:   T + 55…70 мм   (вертельная зона + верх диафиза)
  по ширине: от медиального контура с запасом до латерали/шейки
  масштаб: длинная сторона кропа → 224 или 320 px (аблейшн)

Fallback: если T/маска плохие (флаги rotation:short_window,
rotation:neck_not_reached) — считать полный кадр, как сейчас, с флагом
cnn:full_frame_fallback.

Зачем: CAM текущей сети уже тянется к вертельной области — поле зрения
можно сузить осознанно; на том же размере входа малый вертел занимает
больше пикселей.


3.5. Мультизадача / три класса
------------------------------
Классы по рис. 5 ТЗ:
  норма          — малый вертел слегка деформирует контур
  переротация    — вертела почти нет, контур гладкий
  недоротация    — выступ слишком большой

В отчёт ТЗ по-прежнему бинарь:
  violated = (класс ≠ норма)
В details — subtype: ok / over / under.

Откуда взять 3 метки:
  • суррогат от геометрии: среди expert=1 резать по area vs середина
    коридора (быстро, но зацикливает ошибки контура);
  • лучше: ручная доразметка ~36 нарушений на under/over.

Loss (вариант):
  CE по 3 классам
  + опционально aux-регрессия log(area_mm2) или corridor_distance
    (на инференсе регрессию в вердикт можно не брать).

Инференс:
  p_violation = 1 − p_norm   (или max(p_over, p_under))
  свод с geometry — как сейчас, либо расширенный (см. 3.6).


3.6. Расширенный свод и порог (если AUC есть, а F1 нет)
------------------------------------------------------
Вектор признаков:
  area_mm2, bulge_mm, relative, shaft_mm, corridor_distance,
  флаги neck_not_reached / short_window,
  logit CNN с кропа,
  опционально видимость trochanter_minor из keypoints.

Модель: логистическая регрессия / маленький MLP, коэффициенты — только
вложенный OOF.

Порог:
  • текущее правило «доля нарушений» стабильнее max-F1 на переносе фолдов;
  • имеет смысл пробовать раздельные пороги для over/under;
  • не сравнивать с метриками «подобрали порог на всей выборке».


3.7. План экспериментов
-----------------------
Строго honest OOF / вложенный F1 по folds.csv.

  №1  ResNet-34, бинарь, КРОП, свод как сейчас
      успех: F1 > 0.55 или AUC > 0.82
  №2  ResNet-18, размер кропа 224 vs 320
      успех: не хуже №1, быстрее
  №3  3 класса (суррогат area) → бинарь для метрик ТЗ
      успех: F1 > №1, лучше чувствительность
  №4  расширенный свод (признаки detect + logit кропа)
      успех: вложенный F1 выше текущего правила порога
  №5  ручной subtype на 36 нарушениях (если №3 неоднозначен)

Уже отброшено без новой гипотезы:
  другой энкодер на полном кадре (EfficientNet-B0 хуже);
  только keypoints-признаки;
  CNN на ось (другой критерий).


3.8. Встраивание в код
----------------------
  hip_rotation/detect.py   — rotation_roi_box(img, side, T) → (y0,y1,x0,x1)
  cnn_qc/preprocess.py     — to_input_crop(...)
  cnn_qc/train.py          — --crop, опционально --classes 3
  cnn_qc/predict.py        — assess(..., box=...) ; fallback на полный кадр
  service/pipeline.py      — передать T/box; details.subtype
  overlay                  — CAM с кропа обратно на полный кадр

Время: кроп того же или меньшего размера; ансамбль 3×ResNet-18 на кропе
может быть быстрее текущего 3×ResNet-34 на полном кадре.


3.9. Плюсы и минусы
-------------------
Плюсы:
  • бьёт в самый массовый слабый критерий (36/150);
  • согласован с клинической логикой рис. 5;
  • измерение выступа остаётся в отчёте для оператора;
  • реалистичный путь к общему F1 выше 0.58.

Минусы:
  • 36 позитивов — легко переобучить кроп/порог;
  • суррогат 3 классов от area наследует ошибки контура;
  • переротация ≈ «вертел не найден» при плохой маске — нужен fallback;
  • потолок реалистичен скорее F1 ~0.60–0.65, не 0.9.


3.10. Критерий успеха
---------------------
  • вложенный OOF F1 hip_rotation > 0.55 при AUC не ниже 0.82;
  • нет роста времени выше комфортного запаса до лимита 3 мин;
  • при расхождении CNN и геометрии — по-прежнему флаг
    rotation:cnn_vs_geometry_disagree;
  • subtype (если есть) не ломает формат ТЗ 2.5 (бинарь + коды через ;).

================================================================================
Как приоритизировать 1–3 вместе
================================================================================

Рекомендуемый порядок работ (если ресурсы ограничены):

  1) Подход 2 (сколиоз ≠ наклон)     — быстро, без обучения тяжёлых сетей,
                                       прямой удар по F1 оси и macro-F1.
  2) Подход 3, экспери №1 (кроп)     — главный рычаг общего F1; сначала
                                       бинарь на кропе, потом 3 класса.
  3) Подход 1 (keypoints 2–4)         — параллельно или следом: закрытие Th12
                                       и усиление оси/ROI; ротацию не ждёт.

Зависимости:
  • подход 3 не требует keypoints;
  • подход 1 может позже дать видимость trochanter_minor / iliac / th12
    как доп. признаки в подходы 2–3, но это не блокер;
  • все три обязаны мериться через python -m service.evaluate (honest_oof),
    а не по метрикам с порогом на всей выборке.
