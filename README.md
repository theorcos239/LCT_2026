# Сервис контроля качества денситометрических исследований

Денситометрия (DXA) — рентгеновское измерение плотности костей; по её снимкам
врач судит о риске остеопороза и переломов. Если пациент уложен неправильно,
поле сканирования обрезано или в кадр попал посторонний предмет, измерение
недостоверно, и пациента приходится вызывать повторно. Сервис проверяет
качество снимков DXA поясничного отдела позвоночника и бедра до того, как
исследование уйдёт к врачу: сам определяет, что на снимке, находит нарушения
укладки и границ поля сканирования по пяти критериям ТЗ и объясняет каждое
замечание в миллиметрах и градусах. Работает без интернета и без видеокарты,
на обычном процессоре: 1.6 с на исследование.

На вход подаются снимки в формате DICOM (стандартный формат медицинских
снимков) — как их выгружает денситометр, без какой-либо разметки. На выходе —
таблица, где каждая строка это один снимок: область, класс качества,
перечень нарушений, статус обработки и время. К ней прилагаются JSON со всеми
измерениями, снимки с нанесёнными ориентирами и заключение в формате DICOM SR
(структурированное текстовое заключение, которое PACS — архив снимков
клиники — показывает рядом со снимком).

Честная оценка на 100 обучающих исследованиях (252 снимка; каждый снимок
проверен моделью, которая его не видела): **F1 0.58 и ROC-AUC 0.78** по
классу «есть нарушение», область снимка определена верно на **252 из 252**.
F1 — баланс между найденными нарушениями и ложными тревогами (1.0 — идеал);
ROC-AUC — насколько хорошо оценка отделяет нарушения от нормы (0.5 — наугад,
1.0 — идеально). Что стоит за этими числами — раздел «Критерии и метрики».

**Запуск за пять минут.** Нужен Docker; веса моделей лежат в репозитории,
интернет после сборки образа не нужен:

```bash
./build.sh                              # образ dxa-qc:1.0.0
./run.sh batch /путь/к/исследованиям    # ./out: report.xlsx, details.json, overlays.zip, sr.zip
./run.sh                                # веб-интерфейс и API: http://localhost:8000
```

На Windows без Docker — установщик (таблица ниже). На любой ОС с Python 3.11:

```bash
pip install -r requirements.lock
python -m service.cli /путь/к/исследованиям --out report.xlsx
python -m desktop                       # окно приложения
```

## Что умеет и чего не умеет

**Умеет.** Определяет область снимка (позвоночник / левое бедро / правое
бедро) и отбраковывает кадры, которые вообще не похожи на DXA. Проверяет пять
критериев качества из ТЗ, ставит бинарный класс и перечисляет все сработавшие
нарушения: у одного снимка может быть несколько нарушений сразу — так у 20
исследований из 100, и сервис перечисляет все. Обрабатывает пачку
исследований из папки или zip, пишет xlsx/csv, JSON со всеми измерениями,
zip с визуализацией и текстовое заключение по каждому кадру в формате DICOM SR
(ТЗ 2.6), рисует на снимке найденные ориентиры и тепловую карту нейросети.
Работает целиком локально на процессоре: 1.6 с на исследование (максимум
2.3 с при лимите ТЗ в 3 минуты).

**Не умеет.** Проверять нанесённую оператором разметку — в предоставленных
данных её нет ни в пикселях, ни в тегах (см. [DATASET.md](DATASET.md)).
Работать с денситометрами, кроме GE Lunar Prodigy Advance: масштаб мм/px задан
константой, потому что тег `PixelSpacing` пуст. Ротация бедра остаётся самым
трудным критерием: нейросеть подняла её ROC-AUC с 0.68 до 0.82, но F1 в
честной оценке — 0.55, и ниже сказано почему.

**Где сервис оценивает так же, как эксперт, а не дословно по ТЗ.** Метрики
считаются по разметке эксперта, поэтому мы разобрали, как именно он оценивает.
Отступы области интереса на бедре эксперт судит не по трём отступам с
рисунка 6 ТЗ, а по общей длине поля сканирования: поле должно вмещать 3 см над
большим вертелом, само бедро от вертела до седалищной кости (в среднем 6.9 см)
и ещё 3 см ниже — итого не короче 12.9 см. Такое правило совпадает с
экспертом вдвое чаще, поэтому включено по умолчанию; отступы по рисунку 6 всё
равно измеряются и показываются в отчёте, а буквальное прочтение ТЗ
включается флагом `--roi-rule margins` (`DXA_QC_ROI_RULE=margins`). Цифры и
разбор — в разделе «Критерии и метрики».

## Критерии и метрики

Пять критериев из ТЗ 2.3. Метрики посчитаны на обучающем наборе (100
исследований, 252 уникальных снимка) с 95 % доверительными интервалами:
интервал Уилсона для долей, бутстрэп по **исследованиям** для F1 и AUC
(ТЗ 8.4). ROC-AUC и PR-AUC считаются по непрерывной величине **до** порога
(угол оси в градусах, счёт яркой структуры, вероятность объединённой оценки),
а не по бинарному вердикту: AUC, посчитанная по ответу 0/1, совпадает со
сбалансированной точностью и ничего сверх неё не проверяет. Для бинарного
класса такой величиной служит колонка отчёта `quality_probability =
1 − Π(1 − p)` по калиброванным вероятностям критериев, так что организатор
может посчитать ROC-AUC по ней сам.

**Как читать таблицы.** Чувствительность — какую долю нарушений, отмеченных
экспертом, сервис нашёл; специфичность — какую долю нормальных снимков он не
тронул; F1 — баланс между найденными нарушениями и ложными тревогами (1.0 —
идеал); ROC-AUC — насколько хорошо сервис ранжирует снимки от «точно норма» до
«точно нарушение» независимо от порога (0.5 — случайное угадывание, 1.0 —
идеал); PR-AUC — то же, но с упором на редкий класс нарушений. В квадратных
скобках — 95 % доверительные интервалы: нарушений мало (6–36 на критерий),
поэтому интервалы широкие, и это показано честно.

### Честная оценка: каждый снимок проверен моделью, которая его не видела

Выборка разбита на пять частей (фолдов) так, чтобы все снимки одного
исследования попали в одну часть (`folds.csv`). Для каждой части пороги,
модели и правила объединения подбирались только на остальных четырёх и затем
применялись к ней — это называется out-of-fold и не даёт метрике завыситься
за счёт подгонки под известные ответы. Для позвоночника так подбирается порог;
для ротации бедра и посторонних предметов — коэффициенты объединения
нейросети с геометрией; для отступов ROI правило длины поля взято из ТЗ и
анатомической медианы и по меткам не подбирается вовсе. **Это и есть рабочая
оценка сервиса** (`python -m service.evaluate`, раздел «честная оценка», поле
`honest_oof` в `service/metrics.json`):

|---|---:|---:|---|---|---|---|---:|
| `spine_position` укладка | 99 | 6 | 0.67 [0.30–0.90] | 0.84 [0.75–0.90] | 0.32 [0.08–0.55] | 0.82 [0.58–0.95] | 0.54 |
| `spine_axis` ось > 5° | 99 | 10 | 0.30 [0.11–0.60] | 0.88 [0.79–0.93] | 0.25 [0.00–0.48] | 0.82 [0.72–0.92] | 0.32 |
| `spine_artifacts` предметы | 99 | 17 | 0.65 [0.41–0.83] | 0.93 [0.85–0.97] | 0.65 [0.43–0.81] | 0.85 [0.72–0.96] | 0.63 |
| `hip_rotation` ротация | 150 | 36 | 0.67 [0.50–0.80] | 0.76 [0.68–0.83] | 0.55 [0.39–0.68] | 0.82 [0.72–0.90] | 0.65 |
| `hip_roi` отступы ROI | 150 | 7 | 0.71 [0.36–0.92] | 0.99 [0.95–1.00] | 0.71 [0.22–0.95] | 0.94 [0.82–1.00] | 0.70 |
| позвоночник, кадр | 99 | 31 | 0.65 [0.47–0.79] | 0.68 [0.56–0.78] | 0.55 [0.40–0.68] | 0.72 [0.60–0.83] | 0.56 |
| бедро, кадр | 150 | 41 | 0.71 [0.56–0.82] | 0.75 [0.66–0.82] | 0.60 [0.45–0.72] | 0.82 [0.73–0.90] | 0.69 |
| **всего, «есть нарушение»** | 249 | 72 | 0.68 [0.57–0.78] | 0.72 [0.65–0.78] | 0.58 [0.48–0.66] | 0.78 [0.72–0.85] | 0.62 |

Область снимка определена верно на всех 252 уникальных снимках (100 %,
`region_accuracy` в `service/metrics.json`). Все 499 файлов набора прочитаны
без ошибок; после схлопывания дубликатов из них получены 252 снимка, и все
обработаны (`processed: 252, failed: 0`).

Что дали правило длины поля и нейросеть (`cnn_qc`, раздел «Нейросетевое
второе мнение» ниже) — та же честная оценка, F1 / ROC-AUC. Исходное

| `hip_roi` отступы ROI | 0.35 / 0.89 | **0.71 / 0.94** | **0.71 / 0.94** |
| позвоночник, кадр | 0.49 / 0.64 | 0.49 / 0.64 | **0.55 / 0.72** |

всего 6 положительных примеров, и любой подбор на них — подгонка.

**Отступы ROI бедра: почему сервис судит как эксперт.** Это пример того,
зачем разбирать ошибки вместе с экспертом. Отступы по рисунку 6 ТЗ находят
4 нарушения из 7 при 12 лишних (F1 0.35), хотя само измерение верное: с
ручной разметкой точек вердикт совпадает на 147 кадрах из 147, ROC-AUC 0.89.
Расходится определение. Эксперт ставит «норму» при 1.7–3.0 см под седалищной
костью и «нарушение» на коротких полях, то есть судит по длине поля
сканирования. Правило «поле не короче 3 см над большим вертелом + 6.9 см от
вертела до седалищной кости + 3 см ниже неё», итого 12.9 см, находит 5
нарушений из 7 при 2 лишних: **F1 0.71, ROC-AUC 0.94**. По меткам в нём не
подобрано ничего: 30 мм взяты из ТЗ, а 69 мм от верхушки большого вертела до
седалищной кости — медиана по ручной разметке точек. Поэтому правило длины
поля стоит по умолчанию, а отступы по рисунку 6 считаются всегда и лежат в
отчёте; буквальное прочтение ТЗ — `--roi-rule margins`. Разбор поимённо —
[`DATASET.md`](DATASET.md), раздел «Расхождения сервиса с эталоном: ROI бедра».

Полные таблицы: `service/metrics.json`, `runs/eval_geometry/metrics.json`,
`runs/eval_baseline/metrics.json`, `cnn_qc/*/meta.json`,
`hip_roi/probability.json`, `spine_qc/metrics.json`,
`hip_rotation/metrics.json`, `hip_roi/eval/metrics.json`.

## Расхождения с экспертной оценкой

Эталон метрик — `разметка.xlsx` (ответ организаторов: «других критериев сверх
ТЗ нет, эталон — разметка из xlsx»), и они же попросили отметить расхождения в
документации. Ниже полный их перечень; подробности поимённо — в
[`DATASET.md`](DATASET.md).

| расхождение | масштаб | что делает сервис |
|---|---|---|
| **ROI снизу.** Эталон ставит «норму» при 1.7–3.0 см под седалищной костью, ТЗ требует 3 см | 8 кадров | по умолчанию судит как эксперт — по длине поля сканирования (раздел «Критерии и метрики»); буквальное прочтение рисунка 6 — `--roi-rule margins` |
| **ROI сбоку.** «Норма» при 1.6–1.8 см и «нарушение» при 2.1 см — порядок обратный | 4 кадра | то же |
| **ROI без объяснения.** «Нарушение» при всех трёх отступах от 3.8 см | 2 кадра | `…0069487890`: поле 12.5 см — по длине поля сервис согласен с экспертом; `…4128739670`: поле 15.8 см — вердикт «норма», расхождение зафиксировано |
| **Ось и сколиоз.** При сколиозе эксперт нарушение оси не ставит — ни разу, даже при угле 8.8° | 14 кадров | флаг `axis:curved` (изгиб больше 12 мм); главный источник лишних срабатываний оси |
| **Итог по области ≠ ИЛИ критериев** внутри самой разметки | 3 кадра позвоночника | метрики считаются по критериям, как в ТЗ 8.4 |

Последняя строка — расхождения эталона с самим собой: два исследования
помечены нарушением позвоночника при всех трёх критериях «норма» (у обоих
комментарий «сколиоз»), одно — наоборот, нарушением оси при итоге «норма»
(комментарий «перелом»); у бедра таких случаев нет.

**Что из этого следует для метрик.** Потолок по оси задаёт не наш алгоритм, а
разметка: угол, посчитанный по **ручной разметке точек**, даёт ROC-AUC 0.82 —
ровно столько же, сколько наш измеритель по контуру; эксперт помечает нормой
кадры с наклоном до 12.7° и нарушением — кадры с 2.9°. С отступами ROI так
же: измерение верное, расходится определение. **Эталон не правим:** метки
эксперта используются как есть, расхождения перечислены, а там, где
определение ТЗ и поведение эксперта расходятся, переключение выполняется
одним флагом без переобучения.

## Как устроено решение

```
DICOM → дедупликация → область (region_clf) → критерии области → объединённая оценка → отчёт
                                ↓ не DXA                    ↑
                          ручной разбор            cnn_qc: второе мнение
                                                   (ротация, посторонние предметы)
```

Объединённая оценка (в коде и файлах метрик — «свод») — это итоговое
решение по критерию, которое объединяет геометрическое измерение (миллиметры,
градусы) с вероятностью от нейросети. Там, где нейросети нет, объединённая
оценка — это просто сравнение измерения с порогом.

Основа решения — геометрия, измеряемая в миллиметрах и градусах, плюс
линейные модели на 99–150 примерах. Причина не в экономии ресурсов: при 3–36
положительных примерах на класс сквозную нейросеть учить не на чем, а
геометрический вердикт оператор проверяет глазами за секунду («гребни не
визуализированы», «ось 6.6°»), тогда как вердикт нейросети — нет.

Нейросеть подключена в двух местах, где геометрия упирается в разрешение
снимка, и только вторым мнением: **ротация бедра** (различие между нормой и
ротацией по выступу малого вертела — небольшого костного бугорка на внутренней
стороне бедренной кости — составляет всего около 2 мм) и **посторонние
предметы** (предмет бывает не ярким и не вытянутым). Там вердикт выносит
объединённая оценка нейросети и измерения, измерение остаётся в отчёте, а
нейросеть показывает на снимке тепловую карту — куда она смотрела.

### Две оценки на критерий

Каждый критерий позвоночника и ротация бедра измеряются **двумя независимыми
способами**, и расхождение между ними выносится во флаг. На выборке с шестью
положительными примерами одиночное число нечем проверить, а расхождение двух
оценок — честный признак «здесь измерение ненадёжно». Последняя колонка —
ранговая корреляция двух оценок: чем она ниже, тем более разную информацию
они несут.

| критерий | оценка A (измерение) | оценка B (независимая) | корреляция рангов |
|---|---|---|---|
| ось | угол по центрам тел позвонков | угол по боковым краям колонны | 0.59 |
| укладка | костная масса гребней внизу кадра | вид кадра целиком (логистическая регрессия) | 0.63 |
| артефакты | white top-hat: тонкие яркие структуры | сверточная нейросеть, ансамбль (`cnn_qc`) | 0.29 |
| ротация | выход за коридор нормы по выступу малого вертела | сверточная нейросеть, ансамбль (`cnn_qc`) | 0.33 |

Независимость второй оценки проверена, а не предположена: там, где обе
оценки согласны, специфичность 0.99, а расхождения (32 кадра из 99)
осмысленны. Для оси «вид кадра целиком» оказался бесполезен (AUC 0.57),
поэтому второй оценкой служит другая геометрическая конструкция угла; на
кадрах, где две конструкции сходятся в пределах 2°, F1 оси выше, чем на всех
кадрах (вывод `python -m spine_qc.calibrate --sweep`).

**Для оси и укладки вердикт выносит геометрия, вторая оценка задаёт
уверенность.** Выбор правила проверялся out-of-fold тем же `--sweep`: по
метрикам на всей выборке лучшим для укладки казалось требовать согласия обеих
оценок, но в честной оценке такое правило ловит 1 нарушение из 6. **Для
ротации и посторонних предметов вердикт выносит объединённая оценка**
геометрии и нейросети: там вторая оценка сильнее первой (ROC-AUC нейросети по
ротации 0.80 против 0.68 у выступа), поэтому она входит в объединённую оценку
на равных, а расхождение по-прежнему уходит во флаг
`*:cnn_vs_geometry_disagree`.

### Критерии по областям

**Позвоночник** (`spine_qc/`). Колонна позвоночника разбирается один раз:
маска кости, коридор, левый/правый край и взвешенный центр тела в каждой
строке. Центр берётся внутри **костного отрезка**, содержащего коридор, а не
по окну фиксированной ширины — иначе трек утягивают рёбра и гребни, и AUC оси
падает с 0.83 до 0.57.

- *ось* — прямая Тейла-Сена по центрам тел, угол к вертикали. Порог решения
  4.0°, а не 5° из ТЗ: наш оценщик читает примерно на градус ниже конструкции
  эксперта (медиана на нарушениях 4.0°). Измеренный угол идёт в отчёт как
  есть — вердикт объясним числом. Изгиб больше 12 мм даёт флаг `axis:curved`
  (сколиоз: ось формально вертикальна, позвоночник изогнут). Эксперт при
  сколиозе нарушение оси не ставит — ни в одном из 14 таких кадров, даже при
  угле до 8.8°; это главный источник наших лишних срабатываний оси. Отличить
  сколиоз от наклона по поясничному треку не удалось: нейросеть на оси дала
  ROC-AUC 0.51, то есть сигнала нет.
- *укладка* — доля костных пикселей в нижних боковых зонах кадра, где должны
  быть верхние края подвздошных костей. У всех 6 помеченных экспертом кадров
  она равна нулю против медианы 0.086 у нормы.
- *артефакты* — морфологический фильтр white top-hat, выделяющий тонкие яркие
  структуры: его окно шире посторонней детали (2–4 px) и уже тела позвонка.
  Абсолютная яркость не годится: экспорт Lunar уже насыщен, `max = 255` на
  всех 99 кадрах, и кортикальная кость такая же белая. Счёт = длина ×
  вытянутость × контраст ведущей структуры. Вердикт — объединённая оценка
  этого счёта с вероятностью нейросети `cnn_qc` (ROC-AUC 0.85 против 0.79 у
  одного top-hat, F1 в честной оценке 0.65 против 0.58).

**Бедро.** Отступы ROI — модуль [`hip_roi/`](hip_roi/README.md), комплект
`kit2`. Вердикт по умолчанию — по длине поля сканирования, как оценивает
эксперт (разбор и цифры — раздел «Критерии и метрики»). Отступы по рисунку 6
ТЗ считаются всегда и лежат в отчёте: сверху от верхушки большого вертела
(3 см), сбоку от наружного контура бедренной кости (2 см), снизу от нижней
точки седалищной кости (3 см); с ручной разметкой точек они сходятся с
медианой ошибки не больше 1 мм. Ротация — `hip_rotation/`: выступ малого
вертела над прямой внутреннего контура диафиза. Критерий двусторонний по ТЗ
(переротация — выступа нет, недоротация — выступ слишком большой), поэтому
измерение сравнивается не с порогом, а с коридором нормы 96–272 мм²,
калиброванным по 15-му и 85-му перцентилям корректных кадров; вердикт —
объединённая оценка выхода за коридор с вероятностью нейросети. Оба критерия
опираются на **одну и ту же** верхушку большого вертела.

### Ротация: почему геометрии мало и что добавила нейросеть

Разрыв между классами по выступу малого вертела около 2 мм при ширине диафиза
35 мм, а выступ — это разность двух координат, то есть ошибки складываются.
Чтобы уверенно различать классы по контуру, обе точки нужно находить **точнее
пикселя**. Контурная геометрия этого не даёт: ROC-AUC в честной оценке 0.68.

Что проверено:

| для ротации | OOF ROC-AUC | вывод |
|---|---:|---|
| выступ малого вертела по контуру, коридор нормы | 0.68 | сигнал есть, отсечка грубая |
| вид кадра, логистическая регрессия на 128 px | 0.50 | малый вертел теряется при уменьшении |
| модель ключевых точек, выступ по точкам | — | ошибка выступа 0.75 мм (p90 2.2) сравнима с разрывом классов 2.1 мм |
| сверточная нейросеть на полном кадре, одна модель | 0.76–0.78 | зависит от случайного старта обучения |
| нейросеть, ансамбль трёх случайных стартов | 0.80 | стабильнее одиночной |
| **объединённая оценка нейросети с выступом** | **0.82** | в поставке; F1 в честной оценке 0.55 против 0.48 |

Нейросеть оценивает проксимальный отдел целиком, а не одну разность
координат: на тепловой карте активность приходится на вертельную область и
верх диафиза — туда же, куда смотрит врач по рисунку 5 ТЗ. Модель ключевых
точек этого барьера не взяла: ошибка выступа по предсказанным точкам 0.75 мм
при p90 2.2 всё ещё сравнима с разрывом между классами 2.1 мм
([docs/KEYPOINTS.md](docs/KEYPOINTS.md)). Подробности, включая отвергнутые
варианты, — [`cnn_qc/README.md`](cnn_qc/README.md).

## Нейросетевое второе мнение: `cnn_qc`

ResNet-34, весь кадр, длинная сторона 320 px без искажения пропорций; правое
бедро отражено в левое. Нейросеть ротации стартует с весов ImageNet,
нейросеть посторонних предметов — с энкодера нашей модели ключевых точек,
обученного без отложенной части выборки: она уже знает, где позвонки, и
учится отличать от них чужие структуры (для ротации такой старт не помог и
не взят; происхождение весов — [`cnn_qc/README.md`](cnn_qc/README.md)).
Ансамбль из трёх моделей с разными случайными стартами обучения, ONNX с
весами fp16 (3 × 42.6 МБ на критерий), исполняется `onnxruntime` на
процессоре в один поток — torch рабочему образу не нужен, результат
детерминирован.

Вердикт — объединённая оценка `p = σ(a · logit(p_сети) + b · геометрия + c)`,
то есть логистическая регрессия от двух входов, уверенности нейросети и
измерения; три коэффициента и порог — единственное, что подбирается, порог —
доля нарушений в обучающей выборке. Подбираются они на out-of-fold
вероятностях нейросети; честная оценка вложенная: для каждой части выборки
коэффициенты и порог подобраны на остальных четырёх.

| out-of-fold | ротация, 36 из 150 | предметы, 17 из 99 |
|---|---|---|
| геометрия, ROC-AUC | 0.68 [0.55–0.80] | 0.79 [0.64–0.92] |
| нейросеть, ансамбль, ROC-AUC | 0.80 [0.70–0.89] | 0.83 [0.71–0.94] |
| объединённая оценка, ROC-AUC / PR-AUC | **0.82** [0.72–0.90] / 0.65 | **0.85** [0.72–0.96] / 0.63 |
| вердикт, вложенно: чувствительность / специфичность / F1 | 0.67 / 0.76 / **0.55** | 0.65 / 0.93 / **0.65** |
| геометрия: чувствительность / специфичность / F1 | 0.61 / 0.70 / 0.48 | 0.53 / 0.94 / 0.58 |

Тепловая карта (карта активации класса, CAM) вычисляется той же
ONNX-моделью одновременно с вердиктом и дополнительного времени не требует;
в оверлее она лежит оранжевым поверх снимка (ТЗ 2.6: «тепловая карта»). Нет
onnxruntime или весов — кадр считается геометрией с флагом
`cnn:unavailable(...)`; выключить нейросеть — `--no-cnn` у CLI, `DXA_QC_CNN=0`
у API.

## Входные и выходные данные

**Вход.** Папка с исследованиями, одно исследование, отдельный файл `.dcm` или
zip. Исследование — папка, внутри которой на любой глубине лежат DICOM;
структура подпапок значения не имеет.

Ориентация приводится к стандартному AP-виду по тегу `PatientOrientation`:
вправо по снимку — к левому боку пациента, вниз — к ногам (`L\F`, как у всех
снимков обучающего набора; у четверти тег пуст). Зеркальная выгрузка (`R\F`)
без этого поменяла бы местами левое и правое бедро; она отражается при чтении,
а в `flags` пишется `orientation:mirrored_lr`. Пустой тег кадр не меняет.

Кодирование пикселей: несжатый DICOM (как весь обучающий набор), RLE, JPEG
Baseline, JPEG Lossless, JPEG-LS и JPEG 2000 — без потерь, проверено тестом на
реальном кадре (`python-gdcm` в образе). `MONOCHROME1` инвертируется, VOI LUT
применяется, если задан.

**Выход** — первые восемь колонок ровно как в ТЗ 2.5 и в том же порядке:
`path_to_study`, `study_uid`, `image_uid`, `anatomical_region` (`spine` /
`lh` / `rh` / `unknown`), `quality_class` (0 — качественное, 1 — есть
нарушение), `violation_type` (коды через `;`, например
`spine_axis;spine_artifacts`), `processing_status` (`Success` / `Failure`),
`time_of_processing` (секунды). Дальше — необязательные колонки, которые не
мешают читать обязательную часть: `projection` (ТЗ 2.2: `AP` для принятых
кадров, `unknown` для непринятых), `violation_description` (текст
по-русски), `quality_probability` — калиброванная вероятность «есть
нарушение» (по ней считается ROC-AUC бинарного класса), `p_spine_position`,
`p_spine_axis`, `p_spine_artifacts`, `p_hip_rotation`, `p_hip_roi` —
вероятности по критериям, `region_confidence`, `region_accepted`,
`file_name`, `duplicates`, `flags`, `error`. Описание каждой колонки и
флага — [docs/USER_GUIDE.md](docs/USER_GUIDE.md).

Коды нарушений: `spine_position`, `spine_axis`, `spine_artifacts`,
`hip_rotation`, `hip_roi`, `undetermined`. Список отдаёт `GET /taxonomy`.

Дополнительно: `--details` пишет JSON со всеми измерениями (углы, миллиметры,
флаги, вероятности нейросети), `--overlays` — zip с PNG-визуализацией кадров
с нарушениями (ориентиры, пороги, тепловая карта нейросети), `--sr` — zip с
DICOM SR на каждый обработанный кадр (ТЗ 2.6).

**DICOM SR.** Basic Text SR (`1.2.840.10008.5.1.4.1.1.88.11`): текстовое
заключение по-русски — область, перечень нарушений тем же текстом, что
`violation_description`, флаги — и ссылка на исходный снимок. Теги пациента и
`StudyInstanceUID` копируются с исходного кадра, серия новая
(`Modality = SR`), кодировка UTF-8, так что PACS покажет заключение в том же
исследовании рядом со снимком. SR пишется и для качественных кадров:
«нарушений не обнаружено» — тоже заключение. `VerificationFlag = UNVERIFIED`:
врач его не подписывал. Структурированные измерения (полный TID 1500) в SR не
кладутся сознательно — машиночитаемые числа уже есть в JSON, а SR здесь нужен
человеку.

**Одна строка = один уникальный снимок.** Дубликаты схлопываются по хешу
пикселей внутри исследования: Lunar выгружает один снимок по несколько раз, в
499 файлах обучающего набора всего 252 уникальных кадра, и без дедупликации
исследование даёт до 29 строк вместо трёх. У копий разные `SOPInstanceUID`,
поэтому ловятся они только по пикселям.

## API

```
GET  /                       веб-интерфейс: загрузка, таблица, оверлеи (ТЗ 2.6)
GET  /health                 жив ли сервис, загружены ли модели
GET  /version                версии, пороги, коридоры
GET  /taxonomy               перечень типов нарушений
POST /analyze                один DICOM → вердикт в JSON
POST /analyze/overlay        один DICOM → PNG с визуализацией
POST /analyze/sr             один DICOM → DICOM SR с заключением
POST /batch                  zip с исследованиями → задание (202)
                             ?overlays=true&all_frames=true — оверлеи и для качественных
GET  /jobs, /jobs/{id}       список и статус заданий
GET  /jobs/{id}/report       таблица .xlsx или .csv
GET  /jobs/{id}/details      все измерения в JSON
GET  /jobs/{id}/overlays     zip с визуализацией
GET  /jobs/{id}/sr           zip с DICOM SR
GET  /jobs/{id}/overlays/{uid}.png   визуализация одного кадра (для интерфейса)
GET  /manifest.webmanifest, /sw.js   веб-приложение: установка из браузера,
                             страница «сервис не запущен»
```

Интерактивное описание API — `/docs` (Swagger UI отдаётся из локальной
копии, интернет не нужен).

```bash
curl -F file=@снимок.dcm http://localhost:8000/analyze
curl -F file=@снимок.dcm -OJ http://localhost:8000/analyze/sr
curl -F file=@исследования.zip 'http://localhost:8000/batch?fmt=xlsx&overlays=true&sr=true'
curl -OJ http://localhost:8000/jobs/<id>/report
```

Пакетная обработка выполняется как фоновое задание: закрытый набор может
быть большим, а HTTP-соединение, открытое десятки минут, обычно обрывает
прокси. Для небольших пачек есть `?wait=true` — ответ приходит сразу в том же
запросе.

Ни один эндпоинт не обращается в интернет, изображения за пределы контейнера
не уходят.

## Сборка, запуск, развёртывание

**Требования к серверу (контейнер).** Минимум: 2 ядра CPU x86-64, 2 ГБ RAM, 2 ГБ диска (образ
1.4 ГБ). Рекомендуется 4 ядра и 4 ГБ. **Видеокарта не нужна ни для работы, ни
для калибровки** — только для переобучения нейросети `cnn_qc` (6 минут на
критерий). На тестовой конфигурации (2×H200) сервис использует только
процессор.

**Требования к компьютеру для настольного приложения.** Хватает обычного
офисного компьютера или ноутбука:

| | требование |
|---|---|
| система | Windows 10 или 11, 64 бита; права администратора не нужны |
| процессор | любой 64-разрядный (x86-64) с двумя ядрами и больше. На современном ноутбуке одно исследование обрабатывается за 1.6 с; на более слабом процессоре — дольше, но с большим запасом до лимита ТЗ в три минуты |
| оперативная память | 4 ГБ; сама программа занимает до 0.8 ГБ (измерено на демонстрационном архиве) |
| диск | 1 ГБ свободного места: программа занимает около 520 МБ, установщик — около 290 МБ |
| видеокарта | не нужна |
| интернет | не нужен ни для установки, ни для работы |
| окно приложения | WebView2 Runtime (встроенный в Windows компонент браузера Edge) — есть в Windows 11 и обновлённой Windows 10; без него интерфейс откроется в браузере |

**Зависимости.** Python 3.11 (образ `python:3.11-slim`, закреплён
дайджестом), Docker для контейнерного запуска. Пакеты: numpy и scipy
(геометрия, морфология, статистика), pandas и openpyxl (таблицы, отчёт),
scikit-learn (классификатор области, модели «вида кадра»), pydicom и
python-gdcm (чтение DICOM, в том числе сжатого, запись DICOM SR), pillow
(визуализация), onnxruntime (нейросеть `cnn_qc` на процессоре), fastapi и
uvicorn (HTTP API). Прямые зависимости с версиями — `requirements.txt`;
полный замороженный набор, из которого собирается образ, —
`requirements.lock`. Только для обучения (нейросеть `cnn_qc`, модель ключевых
точек): torch, torchvision, onnx, pyyaml — `requirements-train.txt`.

Производительность (`python -m service.benchmark`, `service/benchmark.json`;
ноутбук с Windows, один процесс, все вычисления в один поток): медиана
**1.6 с на исследование** (p95 1.7 с, максимум 2.3 с при лимите ТЗ в 3
минуты), 444 мс на снимок; все 100 исследований (252 снимка) — 143 с
(2.4 минуты); в контейнере (Linux, Python 3.11) с оверлеями и SR — 158 с.
Почти всё время занимает нейросеть: без неё (`--no-cnn`) 27 мс на снимок.
Исследования независимы, на многоядерной машине пакет параллелится
процессами.

```bash
./build.sh                                # docker build, проверяет наличие весов
./run.sh                                  # интерфейс и API на :8000
./run.sh batch /путь/к/исследованиям      # отчёт + details + overlays + sr в ./out
PORT=9000 ./run.sh                        # другой порт
```

Папка с данными монтируется **только на чтение** — сервис не изменяет исходные
медицинские данные. Скрипты на POSIX sh, работают в том числе там, где
`/bin/sh` это dash или busybox.

Базовый образ закреплён дайджестом (ТЗ 3.2, комментарий в начале
`Dockerfile`); обновляется той же командой, что там указана.

Без Docker:

```bash
python -m pip install -r requirements.txt
python -m service.cli /путь/к/исследованиям --out report.xlsx --overlays overlays.zip
python -m uvicorn service.api:app --host 0.0.0.0 --port 8000
```

Настольное приложение для Windows собирается из того же кода
(`desktop/build_windows.ps1`, PyInstaller и Inno Setup); установщик кладёт в
папку программы все модели и веса, а обновление — это установка новой версии
поверх старой тем же установщиком: файлы заменяются, журналы, отметки
специалиста и токен бота в `%LOCALAPPDATA%`/`%APPDATA%` сохраняются.
Подробности — [docs/DESKTOP.md](docs/DESKTOP.md).

### Воспроизводимость

Повторный запуск на тех же данных даёт побитово тот же результат — это
проверяется тестом. Обеспечивается тремя вещами: все измерения
детерминированы (медианы вместо оптимизации, фиксированный порядок обхода
файлов), модели сохранены на диск, а вычисления идут в один поток — BLAS
(`OMP_NUM_THREADS=1`) и onnxruntime (`intra_op_num_threads = 1`): при
многопоточных вычислениях порядок сложения чисел меняется от запуска к
запуску, и последние знаки результата плавают. Параллелизм при необходимости
берётся процессами на уровне исследований. Обучение нейросети тоже
детерминировано: фиксированные случайные старты и детерминированные
алгоритмы cuDNN.

## Обучение и калибровка

Калибровка геометрии занимает меньше минуты на ноутбуке без видеокарты;
нейросеть `cnn_qc` — около 6 минут на критерий на GPU (на процессоре дольше,
но тоже можно).

```bash
python -m region_clf.make_labels      # эталон области (252 кадра)
python -m region_clf.train --stress   # классификатор области + стресс-тест
python -m spine_qc.calibrate --sweep  # пороги, модель вида кадра, OOF-метрики
python -m hip_rotation.calibrate      # коридор нормы, вероятность ротации
python -m hip_roi.evaluate            # сверка комплектов ROI с экспертом
python -m hip_roi.probability         # вероятность нарушения ROI: длина поля и рисунок 6
python -m cnn_qc.train --criterion rotation    # нейросеть: OOF, объединённая оценка, ансамбль, ONNX
python -m cnn_qc.train --criterion artifacts --init keypoints   # энкодер модели точек, нужны все 5 фолдов
python -m service.evaluate            # сквозные метрики с ДИ + честная оценка
python -m service.evaluate --no-cnn --out runs/eval_geometry/metrics.json
python -m service.evaluate --no-cnn --roi-rule margins --out runs/eval_baseline/metrics.json
python -m service.benchmark           # скорость на всех исследованиях
python -m service.evaluate --keypoints --out runs/metrics_keypoints.json
```

Модель ключевых точек обучается отдельно и дольше остальных (нужен torch,
см. `requirements-train.txt`):

```bash
PYTHONPATH=src python -m dxa_qc.pack --annotations data/*.json \
       --html Processing/razmetka_all.html \
       --studies НД_для_обучения/Исследования --out data/keypoints.npz
PYTHONPATH=src python -m dxa_qc.train --config configs/keypoints.yaml
```

`src/` пакетом не ставится, поэтому `PYTHONPATH=src`. Подробно — дообучение,
перенос на другой аппарат, разбиение на части — в
[docs/TRAINING.md](docs/TRAINING.md). Разбиение на пять частей фиксировано в
`folds.csv`, и код его только читает; группа — **исследование**: два бедра
одного пациента похожи, и разойдись они по разным частям, метрика оказалась
бы завышенной. Данные для калибровки и обучения в репозиторий не
входят: набор организаторов `НД_для_обучения/`, файл разметки
`Processing/razmetka_all.html` и собранный `data/keypoints.npz` содержат
снимки, поэтому хранятся только локально, рядом с кодом (в образ они не
копируются).

## Модель ключевых точек

Экспериментальная модель, по умолчанию выключена. U-Net с энкодером ResNet-34
предсказывает 29 анатомических точек (21 на позвоночнике, 8 на бедре) по
нашей собственной разметке 242 кадров. В поставке обучены 2 части выборки из
5. На этих кадрах она честно (out-of-fold) сравнивалась с контурной
геометрией: macro-F1 0.571 против 0.541, по оси F1 0.50 против 0.33 — но всего
на четырёх нарушениях оси, и в 12 раз медленнее (347 мс против 28 мс на кадр).
Ротацию она не улучшает: ошибка выступа малого вертела по точкам 0.75 мм
(p90 2.2) сопоставима с разрывом между классами 2.1 мм. Поэтому по умолчанию
вердикт остаётся за контуром; включение — `--keypoints` (CLI) или
`DXA_QC_KEYPOINTS=1` (API), torch при этом нужен только для этого режима, а
отсутствие весов или torch сервис не роняет (флаг `keypoints:unavailable(...)`).
Полный разбор — архитектура, ошибки по каждой точке, исправленные ошибки
предыдущей версии, что нужно для включения по умолчанию — в
[docs/KEYPOINTS.md](docs/KEYPOINTS.md).

## Известные ошибки и как они обрабатываются

Необработанных исключений наружу не выходит (ТЗ 2.7): любая ошибка становится
строкой отчёта со статусом `Failure`, текстом в `error` и `quality_class = 1` —
непрочитанный кадр не считается качественным.

| ситуация | поведение |
|---|---|
| битый или не-DICOM файл | строка `Failure`, пачка продолжается |
| сжатый DICOM (RLE, JPEG, JPEG-LS, JPEG 2000) | читается штатно, пиксели совпадают с несжатым |
| DICOMDIR, SR/PDF-отчёты, `.DS_Store`, `__MACOSX/` рядом со снимками | не снимки — строк не дают; DICOMDIR в корне не склеивает выгрузку в одно исследование |
| пустая папка исследования | строка `Failure` с пояснением |
| кадр не похож на DXA | `anatomical_region = unknown`, `violation_type = undetermined`, уходит на ручной разбор |
| перевёрнутый кадр | ловится проверкой ориентации в `region_clf` (100 % на суррогатах) |
| зеркальная выгрузка, `PatientOrientation = R\F` | кадр отражается к стандартному виду, сторона бедра определяется верно (тест), флаг `orientation:mirrored_lr` |
| эндопротез | область определяется верно, критерии считаются; эксперт такие бёдра не оценивал |
| нетипичный размер, нули, константа, шум | конвейер отрабатывает без исключений (тест) |
| path traversal в zip | распаковка отклоняется |
| седалищная кость не найдена на кадре (полутоновые кадры) | повтор по строгой маске (`I:strict_mask`); если и это не помогло, отступ снизу оценивается по среднему расстоянию «вертел + 69 мм» (`I:anatomical_prior`) и помечается как неуверенный; на вердикт по длине поля (по умолчанию) не влияет |
| сколиоз | флаг `axis:curved`; эксперт сколиоз нарушением оси не считает, а сервис по углу может поставить `spine_axis` (раздел «Критерии по областям») |
| расхождение двух оценок критерия | флаг `*:estimates_disagree`, уверенность low |
| нейросеть и геометрия расходятся (ротация, предметы) | вердикт по объединённой оценке, флаг `*:cnn_vs_geometry_disagree`, уверенность low |
| нет onnxruntime или весов нейросети | кадр считается геометрией, флаг `cnn:unavailable(...)` — сервис не падает |
| снимок 12 или 16 бит | для нейросети яркость нормализуется по перцентилям 0.5–99.5, геометрия работает в своих единицах |

Флаги едут в колонке `flags` и в JSON измерений.

## Ограничения

- **Один аппарат.** Все 100 исследований сняты на GE Lunar Prodigy Advance.
  Масштаб 0.600 мм/px для позвоночника и 0.607 для бедра задан константой,
  потому что `PixelSpacing` пуст, а `ExposedArea` ненадёжен. На другом
  денситометре константу надо перепроверить, а модели переобучить — это минута.
- **Нанесённая оператором разметка не проверяется**: её нет в данных — ни
  ROI, ни линий, ни оверлеев. По ответу организаторов других критериев сверх
  ТЗ нет, а эталон — `разметка.xlsx`; «корректность области интересов» в нём —
  это отступы поля сканирования бедра, их сервис и проверяет. Все пять
  критериев оцениваются по самому изображению.
- **ROI бедра — как эксперт, а не дословно по рисунку 6**; буквальное
  прочтение ТЗ — `--roi-rule margins`, без переобучения (раздел «Критерии и
  метрики»). Какое определение считать эталонным, решают организаторы.
- **Ось и сколиоз.** Эксперт не ставит нарушение оси при сколиозе, сервис по
  углу — может (раздел «Критерии по областям»). Нужна разметка сколиоза или
  снимки грудного отдела.
- **Верхняя граница укладки (половина тела Th12) не проверяется.** Разметки
  уровня Th12 в данных нет, проверять правило не на чем. Запас кадра сверху
  считается и кладётся в отчёт как диагностика, но в вердикт не входит.
- **Ротация бедра** — самый трудный критерий: ROC-AUC объединённой оценки
  0.82, но F1 в честной оценке 0.55. При расхождении нейросети и выступа кадр
  помечается флагом.
- **Нейросеть обучена на одном аппарате и 99–150 снимках.** На другом
  денситометре её нужно дообучить тем же скриптом (`python -m cnn_qc.train`);
  яркость для нейросети нормализуется по перцентилям, так что 12-битный вход
  её не сломает, но другой вид снимка — может. Тепловая карта нейросети
  грубая (10 × 10 на кадр): она показывает область, а не точку.
- **Статистики мало.** 3–36 положительных примеров на критерий; доверительные
  интервалы широкие, и это видно в таблицах. Разницу между вариантами
  алгоритма в пределах интервала считать значимой нельзя.
- **Фильтр чужих кадров проверен на суррогатах** (искажениях своих же кадров),
  а не на настоящих снимках предплечья или всего тела — их в наборе нет.
- **Модель ключевых точек по умолчанию выключена и обучена на двух частях
  выборки из пяти**; подключается флагом `--keypoints`. Разбор — раздел
  «Модель ключевых точек» и [docs/KEYPOINTS.md](docs/KEYPOINTS.md).

## Что дальше

1. Пилот в теневом режиме (DICOM-роутер → контейнер → SR в PACS), отметки
   операторов «согласен / не согласен» из веб-интерфейса — в перекалибровку
   порогов и объединённой оценки раз в месяц.
2. Больше положительных примеров ротации и оси: F1 ротации 0.55 при ROC-AUC
   0.82 в честной оценке означает, что ранжирование лучше отсечки, а отсечку
   на 36 примерах устойчиво не подобрать.
3. Модель ключевых точек: дообучить оставшиеся три части выборки и повторить
   сравнение с контуром на всём наборе; видимость гребней подвздошных костей —
   кандидат в вердикт укладки, когда нарушений будет больше шести.
4. Второй аппарат (Hologic): проверка масштаба и дообучение нейросети.
5. Обновление и интеграция. Сейчас новая версия настольного приложения — это
   новый установщик поверх старого; следующий шаг — проверка версии и
   скачивание обновления из окна приложения по явному согласию пользователя.
   Встраивание в PACS, МИС и другие сервисы медорганизации: Telegram-бот —
   прототип такой интеграции, тот же анализ отвечает в чужом интерфейсе.
