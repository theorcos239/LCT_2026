# Сервис контроля качества денситометрических исследований

Автоматическая оценка качества DXA-исследований поясничного отдела позвоночника
и проксимального отдела бедра: определение анатомической области, проверка
укладки и разметки по критериям ТЗ, выдача структурированного отчёта.

На вход — DICOM без разметки. На выходе — таблица, где каждая строка это один
снимок: область, класс качества, перечень нарушений, статус обработки и время.

```bash
./build.sh                                   # собрать контейнер
./run.sh batch /путь/к/исследованиям         # отчёт в ./out/report.xlsx
./run.sh                                     # веб-интерфейс и API на localhost:8000
```

**Проверяющим** — [docs/REVIEW.md](docs/REVIEW.md): отчёт на закрытом наборе
за пять минут и таблица «пункт ТЗ → где закрыт → как проверить».

Один и тот же конвейер доступен через четыре интерфейса — отчёты у них
совпадают побитово:

| интерфейс | для чего | как открыть |
|---|---|---|
| **контейнер** | пакетная обработка, API, веб-интерфейс на сервере | `./build.sh`, `./run.sh` — ниже в этом README |
| **веб-приложение** | загрузка папки или zip, снимки с разметкой, отметки специалиста, выгрузки; устанавливается из браузера как приложение | `http://localhost:8000/` — [USER_GUIDE.md](docs/USER_GUIDE.md) |
| **настольное приложение для Windows** | то же без Docker: установщик, окно, пакетная обработка из консоли | [DXA-QC-Setup-1.0.0.exe](https://github.com/theorcos239/LCT_2026/raw/master/release/DXA-QC-Setup-1.0.0.exe) (288 МБ, [release/](release/README.md)) — [DESKTOP.md](docs/DESKTOP.md) |
| **Telegram-бот** | показать сервис с телефона; только обезличенные данные | [@LCT_bone_density_research_bot](https://t.me/LCT_bone_density_research_bot) — [TELEGRAM_BOT.md](docs/TELEGRAM_BOT.md) |

## Что умеет и чего не умеет

**Умеет.** Определяет область снимка (позвоночник / левое бедро / правое
бедро) и отбраковывает кадры, которые вообще не похожи на DXA. Проверяет пять
критериев качества из ТЗ, ставит бинарный класс и перечисляет все сработавшие
нарушения — задача мультилейбловая, у 20 исследований из 100 нарушение не
одно. Обрабатывает пачку исследований из папки или zip, пишет xlsx/csv, JSON
со всеми измерениями, zip с визуализацией и текстовое заключение по каждому
кадру в формате DICOM SR (ТЗ 2.6), рисует на снимке найденные ориентиры и
тепловую карту нейросети. Работает целиком локально на CPU:
1.6 с на исследование (максимум 2.3 с при лимите ТЗ в 3 минуты).

**Не умеет.** Проверять нанесённую оператором разметку — в предоставленных
данных её нет ни в пикселях, ни в тегах (см. [DATASET.md](DATASET.md)).
Работать с денситометрами, кроме GE Lunar Prodigy Advance: масштаб мм/px задан
константой, потому что `PixelSpacing` пуст. Ротация бедра остаётся самым
трудным критерием: сеть подняла её ROC-AUC с 0.68 до 0.82, но F1 out-of-fold —
0.55, и ниже сказано почему.

**Где сервис следует эксперту, а не букве ТЗ.** Метрики на закрытой выборке
считаются по разметке эксперта, поэтому мы разобрали, как он оценивает. Отступы
ROI бедра эксперт судит по **длине поля сканирования**, а не по отступам от
ориентиров рисунка 6: правило «поле не короче 3 см + вертел — седалищная кость +
3 см» совпадает с ним вдвое лучше (F1 0.71 против 0.35). Оно и стоит по
умолчанию; отступы по рисунку 6 считаются всегда и показываются в отчёте и
интерфейсе, а режим строго по ТЗ — `--roi-rule margins` (`DXA_QC_ROI_RULE=margins`).

## Критерии и метрики

Пять критериев из ТЗ 2.3. Метрики — на обучающем наборе (100 исследований,
252 уникальных снимка), 95% доверительные интервалы: Уилсон для долей,
бутстрэп по **исследованиям** для F1 и AUC (ТЗ 8.4). ROC-AUC и PR-AUC — по
непрерывной величине **до** порога (угол оси в градусах, счёт top-hat,
вероятность свода с сетью), а не по бинарному вердикту: ранговая AUC на
0/1-предсказании совпадает со сбалансированной точностью и не проверяет ничего
сверх неё. Для бинарного класса такой величиной служит `quality_probability =
1 − Π(1 − p)` по калиброванным вероятностям критериев — та же колонка, что в
отчёте, так что организатор может посчитать ROC-AUC по ней.

## Расхождения с экспертной оценкой

Эталон метрик — `разметка.xlsx` (ответ организаторов: «других критериев сверх
ТЗ нет, эталон — разметка из xlsx»), и они же попросили отметить расхождения в
документации. Ниже полный их перечень; подробности поимённо — в
[`DATASET.md`](DATASET.md).

| расхождение | масштаб | что делает сервис |
|---|---|---|
| **ROI снизу.** Эталон ставит «норму» при 1.7–3.0 см под седалищной костью, ТЗ требует 3 см | 8 кадров | по умолчанию судит как эксперт — по длине поля (F1 0.71 против 0.35); режим строго по рисунку 6 — `--roi-rule margins` |
| **ROI сбоку.** «Норма» при 1.6–1.8 см и «нарушение» при 2.1 см — порядок обратный | 4 кадра | то же |
| **ROI без объяснения.** «Нарушение» при всех трёх отступах от 3.8 см | 2 кадра | вердикт «норма», расхождение зафиксировано |
| **Ось и сколиоз.** При сколиозе эксперт нарушение оси не ставит — ни разу, даже при угле 8.8° | 14 кадров | флаг `axis:curved` (изгиб больше 12 мм); главный источник лишних срабатываний оси |
| **Итог по области ≠ ИЛИ критериев** внутри самой разметки | 3 кадра позвоночника | метрики считаются по критериям, как в ТЗ 8.4 |

Последняя строка — расхождения эталона с самим собой: `…4821772940` и
`…5571570912` помечены нарушением позвоночника при всех трёх критериях
«норма» (у обоих комментарий «сколиоз»), `…0069487890` — наоборот, нарушение
оси при итоге «норма» (комментарий «перелом»). У бедра таких случаев нет.
Это же исследование `…0069487890` даёт одно из двух необъяснённых расхождений
по ROI — то есть трудные для эксперта кадры группируются.

**Что из этого следует для метрик.** Потолок по оси — не наш алгоритм, а
разметка: угол, посчитанный по **ручной разметке точек**, даёт ROC-AUC 0.82,
ровно столько же, сколько контурный измеритель. Эксперт помечает нормой кадры
с наклоном до 12.7° и нарушением — кадры с 2.9°. Аналогично по ROI: вердикт
сервиса совпадает с вердиктом по ручным точкам на 147 кадрах из 147, то есть
измерение верное, расходится определение.

**Эталон не правим.** Метки эксперта используются как есть, расхождения
перечислены, а там, где определение ТЗ и поведение эксперта расходятся,
переключение — одним флагом без переобучения.

## Как устроено решение

```
DICOM → дедупликация → область (region_clf) → критерии области → свод → отчёт
                                ↓ не DXA          ↑
                          ручной разбор     cnn_qc: второе мнение
                                            (ротация, посторонние предметы)
```

Основа решения — геометрия, измеряемая в миллиметрах и градусах, плюс
линейные модели на 99–150 примерах. Причина не в экономии: при 3–36
положительных примерах на класс сквозную сеть учить не на чем, а
геометрический вердикт оператор проверяет глазами за секунду («гребни не
визуализированы», «ось 6.6°»), тогда как вердикт сети — нет.

Сеть подключена в двух местах, где геометрия упирается в разрешение, и только
вторым мнением: **ротация бедра** (разрыв классов по выступу малого вертела
около 2 мм) и **посторонние предметы** (предмет бывает не ярким и не
вытянутым). Там вердикт выносит свод сети с измерением, измерение остаётся в
отчёте, а сеть показывает на снимке тепловую карту — куда она смотрела.

### Две оценки на критерий

Каждый критерий позвоночника и ротация бедра измеряются **двумя независимыми
способами**, и расхождение выносится во флаг. На выборке с шестью
положительными примерами одиночное число нечем проверить; расхождение двух
оценок — честный признак «здесь измерение ненадёжно».

| критерий | оценка A (измерение) | оценка B (независимая) | корр. рангов |
|---|---|---|---|
| ось | угол по центрам тел позвонков | угол по боковым краям колонны | 0.59 |
| укладка | костная масса гребней внизу кадра | вид кадра целиком (лог. регрессия) | 0.63 |
| артефакты | white top-hat: тонкие яркие структуры | сверточная сеть, ансамбль (`cnn_qc`) | 0.29 |
| ротация | выход за коридор нормы по выступу малого вертела | сверточная сеть, ансамбль (`cnn_qc`) | 0.33 |

Независимость здесь проверена, а не предположена. Первая версия сверяла
морфологию top-hat с регрессией, обученной **на тех же четырёх признаках** —
оценки разошлись на 1 кадре из 99, то есть не проверяли ничего. После замены
второй оценки на «вид кадра целиком» расхождений стало 32, и они осмысленны:
там, где обе оценки согласны, специфичность 0.99. Для оси такая же проверка
показала, что вид кадра бесполезен (AUC 0.57), и второй оценкой стала другая
геометрическая конструкция угла — на кадрах, где две конструкции сходятся в
пределах 2°, F1 критерия 0.50 против 0.41 на всех кадрах.

**Для оси и укладки вердикт выносит геометрия, вторая оценка задаёт
уверенность.** Выбор правила проверялся по OOF (`python -m spine_qc.calibrate
--sweep`): по метрикам на всей выборке лучшим для укладки казалось согласие
обеих оценок (F1 0.73), но out-of-fold оно ловит 1 нарушение из 6. **Для
ротации и посторонних предметов вердикт выносит свод** геометрии и сети — там
вторая оценка сильнее первой (ROC-AUC сети по ротации 0.80 против 0.68 у
выступа), и в свод она входит на равных, а расхождение по-прежнему уходит во
флаг `*:cnn_vs_geometry_disagree`.

### Критерии по областям

**Позвоночник** (`spine_qc/`). Колонна позвоночника разбирается один раз:
маска кости, коридор, левый/правый край и взвешенный центр тела в каждой
строке. Центр берётся внутри **костного отрезка**, содержащего коридор, а не
по окну фиксированной ширины — иначе трек утягивают рёбра и гребни, и AUC оси
падает с 0.83 до 0.57.

- *ось* — прямая Тейла-Сена по центрам тел, угол к вертикали. Порог решения
  4.0°, а не 5° из ТЗ: наш оценщик читает примерно на градус ниже конструкции
  эксперта (медиана на нарушениях 4.0°). Измеренный угол идёт в отчёт как
  есть — вердикт объясним числом. Изгиб больше 12 мм даёт флаг `axis:curved`
  (сколиоз: ось формально вертикальна, позвоночник изогнут). Эксперт при
  сколиозе нарушение оси не ставит — ни в одном из 14 таких кадров, даже при
  угле до 8.8°; это главный источник наших лишних срабатываний оси. Отличить
  сколиоз от наклона по поясничному треку не удалось: сеть на оси дала ROC-AUC
  0.51, то есть сигнала нет.
- *укладка* — доля костных пикселей в нижних латеральных зонах, прокси верхних
  краёв подвздошных костей. У всех 6 помеченных экспертом кадров она равна
  нулю против медианы 0.086 у нормы.
- *артефакты* — white top-hat со структурным элементом шире косточки белья
  (2–4 px) и уже тела позвонка. Абсолютная яркость не годится: экспорт Lunar
  уже насыщен, `max = 255` на всех 99 кадрах, и кортикальная кость такая же
  белая. Счёт = длина × вытянутость × контраст ведущей структуры. Вердикт —
  свод этого счёта с вероятностью сети `cnn_qc` (ROC-AUC 0.85 против 0.79 у
  одного top-hat, F1 out-of-fold 0.65 против 0.58).

**Бедро.** Отступы ROI — модуль [`hip_roi/`](hip_roi/README.md), комплект
`kit2`. Вердикт по умолчанию — **длина поля сканирования**, как оценивает
эксперт: поле по вертикали не короче 3 см + 6.9 см + 3 см = 12.9 см, где 6.9 см —
медиана расстояния от верхушки большого вертела до нижней точки седалищной
кости по ручной разметке 149 кадров (1–99 перцентиль 52–83 мм). Отступы по
рисунку 6 ТЗ и ответу организаторов считаются всегда и лежат в отчёте: от
области интереса до границы поля — сверху от верхушки большого вертела (3 см),
сбоку от наружного контура бедренной кости (2 см), снизу от нижней точки
седалищной кости (3 см). С ручной разметкой точек они сходятся с медианой
ошибки 1 мм и меньше, вердикт по ним совпадает на 147 кадрах из 147; вердикт
строго по рисунку 6 — `--roi-rule margins`. Ротация —
`hip_rotation/`: выступ малого вертела над прямой медиального контура
диафиза. Оба критерия опираются на **одну и ту же** верхушку большого
вертела, а не на две независимые.

Критерий ротации двусторонний по ТЗ (переротация — выступа нет, недоротация —
выступ слишком большой), поэтому измерение сравнивается не с порогом, а с
коридором нормы 96–272 мм², калиброванным по 15-му и 85-му перцентилям
корректных кадров. Вердикт — свод выхода за коридор с вероятностью сети.

### Ротация: почему геометрии мало и что добавила сеть

Разрыв между классами по выступу малого вертела около 2 мм при ширине диафиза
35 мм, а выступ — это разность двух координат, то есть ошибки складываются.
Чтобы уверенно различать классы по контуру, обе точки нужно находить **точнее
пикселя**. Контурная геометрия этого не даёт: OOF ROC-AUC 0.68.

Что проверено:

| для ротации | OOF ROC-AUC | вывод |
|---|---:|---|
| выступ малого вертела по контуру, коридор нормы | 0.68 | сигнал есть, отсечка грубая |
| вид кадра, логистическая регрессия на 128 px | 0.50 | малый вертел теряется при уменьшении |
| модель ключевых точек, выступ по точкам | — | ошибка выступа 0.63 мм (p90 1.73) сравнима с разрывом классов 2.1 мм |
| сверточная сеть на полном кадре, одна модель | 0.76–0.78 | зависит от сида |
| сеть, ансамбль трёх сидов | 0.80 | стабильнее одиночной |
| **свод сети с выступом** | **0.82** | в поставке; F1 вложенно 0.55 против 0.48 |

Сеть оценивает проксимальный отдел целиком, а не одну разность координат:
на тепловой карте активность приходится на вертельную область и верх
диафиза — туда же, куда смотрит врач по рисунку 5 ТЗ.
Подробности, включая отвергнутые варианты, — [`cnn_qc/README.md`](cnn_qc/README.md).

**Модель точек этого барьера не взяла.** Обучена на всех 242 размеченных
кадрах, 5 фолдов; ошибка выступа по предсказанным точкам out-of-fold 0.63 мм
при p90 1.73 — всё ещё сравнимо с разрывом между классами 2.1 мм. Признаки по
точкам (длина шейки, положение малого вертела относительно диафиза,
шеечно-диафизарный угол) по OOF-точкам дают ROC-AUC не выше 0.66.

Два промежуточных результата зафиксированы, чтобы их не повторяли:
измерение без остановки на входе в шейку даёт 60–70 мм вместо 3–8 мм (максимум
отклонения приходится на медиальный край шейки), а модель по виду кадра для
ротации бесполезна (AUC 0.50) — выступ слишком мелкая деталь для уменьшенного
кадра; сети нужен кадр в исходном разрешении.

## Нейросетевое второе мнение: `cnn_qc`

ResNet-34, весь кадр, длинная сторона 320 px без искажения пропорций; правое
бедро отражено в левое. Энкодер сети ротации — ImageNet, сети посторонних
предметов — энкодер нашей модели ключевых точек (для фолда k — модели,
обученной без фолда k, так что отложенные снимки не видела ни одна из двух
сетей): она уже знает, где позвонки, и учится отличать от них чужие
структуры. Для ротации такой старт не помог (ROC-AUC 0.79 против 0.80) и не
взят. Ансамбль из трёх моделей (сиды 0–2),
ONNX с весами fp16 (3 × 42.6 МБ на критерий), исполняется `onnxruntime` на CPU
в один поток — torch рабочему образу не нужен, результат детерминирован.

Вердикт — свод `p = σ(a · logit(p_сети) + b · геометрия + c)`, порог — доля
нарушений в обучающей выборке. Три коэффициента и порог подбираются на
out-of-fold вероятностях сети; честная оценка вложенная — для каждого фолда
свод и порог подобраны на остальных четырёх.

| out-of-fold | ротация, 36 из 150 | предметы, 17 из 99 |
|---|---|---|
| геометрия, ROC-AUC | 0.68 [0.55–0.80] | 0.79 [0.64–0.92] |
| сеть, ансамбль, ROC-AUC | 0.80 [0.70–0.89] | 0.83 [0.71–0.94] |
| свод, ROC-AUC / PR-AUC | **0.82** [0.72–0.90] / 0.65 | **0.85** [0.72–0.96] / 0.63 |
| вердикт, вложенно: чувств. / специф. / F1 | 0.67 / 0.76 / **0.55** | 0.65 / 0.93 / **0.65** |
| геометрия: чувств. / специф. / F1 | 0.61 / 0.70 / 0.48 | 0.53 / 0.94 / 0.58 |

Карта активации класса (CAM) — выход той же ONNX-модели (логит равен
среднему по карте), поэтому объяснение ничего не стоит: в оверлее она лежит
оранжевым поверх снимка (ТЗ 2.6: «тепловая карта»). Нет onnxruntime или весов —
кадр считается геометрией с флагом `cnn:unavailable(...)`; выключить сеть —
`--no-cnn` у CLI, `DXA_QC_CNN=0` у API.

## Входные и выходные данные

**Вход.** Папка с исследованиями, одно исследование, отдельный файл `.dcm` или
zip. Исследование — папка, внутри которой на любой глубине лежат DICOM;
структура подпапок значения не имеет.

Ориентация приводится к стандартному AP-виду по `PatientOrientation`: вправо
по снимку — к левому боку пациента, вниз — к ногам (`L\F`, как у всех снимков
обучающего набора, у четверти тег пуст). Зеркальная выгрузка (`R\F`) без этого
поменяла бы местами левое и правое бедро; она отражается при чтении, а в
`flags` пишется `orientation:mirrored_lr`. Пустой тег кадр не меняет.

Кодирование пикселей: несжатый DICOM (как весь обучающий набор), RLE, JPEG
Baseline, JPEG Lossless, JPEG-LS и JPEG 2000 — без потерь проверено тестом на
реальном кадре (`python-gdcm` в образе). `MONOCHROME1` инвертируется, VOI LUT
применяется, если задан.

**Выход** — первые восемь колонок ровно как в ТЗ 2.5 и в том же порядке:

| колонка | значение |
|---|---|
| `path_to_study` | путь к исследованию |
| `study_uid` | `StudyInstanceUID` из тегов |
| `image_uid` | `SOPInstanceUID` из тегов |
| `anatomical_region` | `spine` / `lh` / `rh` / `unknown` |
| `quality_class` | 0 — качественное, 1 — есть нарушение |
| `violation_type` | коды через `;`, например `spine_axis;spine_artifacts` |
| `processing_status` | `Success` / `Failure` |
| `time_of_processing` | секунды, float |

Дальше — необязательные колонки, которые не мешают читать обязательную часть:
`projection` — проекция (ТЗ 2.2: «область и проекция»): `AP` для принятых
кадров позвоночника и бедра, `unknown` для непринятых; `violation_description`
(текст по-русски), `quality_probability` —
калиброванная вероятность «есть нарушение» (по ней считается ROC-AUC
бинарного класса), `p_spine_position`, `p_spine_axis`, `p_spine_artifacts`,
`p_hip_rotation`, `p_hip_roi` — вероятности по критериям, `region_confidence`,
`region_accepted`, `file_name`, `duplicates`, `flags`, `error`.

Коды нарушений: `spine_position`, `spine_axis`, `spine_artifacts`,
`hip_rotation`, `hip_roi`, `undetermined`. Список отдаёт `GET /taxonomy`.

Дополнительно: `--details` пишет JSON со всеми измерениями (углы, миллиметры,
флаги, вероятности сети), `--overlays` — zip с PNG-визуализацией кадров с
нарушениями (ориентиры, пороги, тепловая карта сети), `--sr` —
zip с DICOM SR на каждый обработанный кадр (ТЗ 2.6).

**DICOM SR.** Basic Text SR (`1.2.840.10008.5.1.4.1.1.88.11`): корневой
контейнер «Findings» с текстовым заключением по-русски — область и перечень
нарушений тем же текстом, что `violation_description`, плюс флаги — и ссылкой
на исходный снимок. Теги пациента и `StudyInstanceUID` копируются с исходного
кадра, серия новая (`Modality = SR`), кодировка UTF-8 (`ISO_IR 192`), так что
PACS покажет заключение в том же исследовании рядом со снимком. SR пишется и
для качественных кадров: «нарушений не обнаружено» — тоже заключение.
`VerificationFlag = UNVERIFIED`: врач его не подписывал. Полный TID 1500 со
структурированными измерениями не делался сознательно — машиночитаемые числа
уже есть в JSON, а SR здесь нужен человеку.

**Одна строка = один уникальный снимок.** Дубликаты схлопываются по хешу
пикселей внутри исследования: Lunar выгружает один снимок по несколько раз, в
499 файлах обучающего набора всего 252 уникальных кадра, и без дедупликации
исследование даёт до 29 строк вместо трёх. У копий разные `SOPInstanceUID`,
поэтому ловятся они только по пикселям.

## API

```
GET  /                       веб-интерфейс: загрузка, таблица, оверлеи (ТЗ 2.6)

POST /analyze/sr             один DICOM → DICOM SR с заключением
POST /batch                  zip с исследованиями → задание (202)
                             ?overlays=true&all_frames=true — оверлеи и для качественных
GET  /jobs, /jobs/{id}       список и статус заданий
GET  /jobs/{id}/report       таблица .xlsx или .csv
GET  /jobs/{id}/details      все измерения в JSON
GET  /jobs/{id}/overlays     zip с визуализацией
GET  /jobs/{id}/sr           zip с DICOM SR
GET  /jobs/{id}/overlays/{uid}.png   визуализация одного кадра (для интерфейса)
GET  /manifest.webmanifest, /sw.js   веб-приложение: установка из браузера,
                             страница «сервис не запущен»
```

Интерактивная документация — `/docs`.

```bash
curl -F file=@снимок.dcm http://localhost:8000/analyze
curl -F file=@снимок.dcm -OJ http://localhost:8000/analyze/sr
curl -F file=@исследования.zip 'http://localhost:8000/batch?fmt=xlsx&overlays=true&sr=true'
curl -OJ http://localhost:8000/jobs/<id>/report
```

Пакетная обработка идёт заданием в фоне: закрытый тестовый набор может
оказаться большим, а держать HTTP-соединение открытым полчаса — надёжный
способ получить таймаут на прокси. Для небольших пачек есть `?wait=true`.

Ни один эндпоинт не ходит в сеть, изображения за пределы контейнера не уходят.

## Сборка, запуск, развёртывание

**Требования.** Минимум: 2 ядра CPU x86-64, 2 ГБ RAM, 2 ГБ диска (образ
1.4 ГБ). Рекомендуется 4 ядра и 4 ГБ. **GPU не нужен ни для инференса, ни для
калибровки** — только для переобучения сети `cnn_qc` (6 минут на критерий).
На тестовой конфигурации (2×H200) сервис использует только CPU.

**Зависимости.** Python 3.11 (образ `python:3.11-slim`, закреплён
дайджестом), Docker для контейнерного запуска. Python-пакеты:

| пакет | версия | зачем |
|---|---|---|
| numpy, scipy | 2.3.5, 1.16.3 | геометрия, морфология, статистика |
| pandas | 3.0.5 | таблицы, отчёт |
| scikit-learn, joblib | 1.9.0, 1.5.3 | классификатор области, модели «вида кадра» |
| pydicom | 3.0.2 | чтение DICOM, запись DICOM SR |
| python-gdcm | 3.2.6 | декодер сжатых DICOM (JPEG Lossless, JPEG-LS) |
| pillow | 12.0.0 | визуализация, JPEG/JPEG 2000 |
| openpyxl | 3.1.5 | запись .xlsx |
| onnxruntime | 1.30.0 | сеть `cnn_qc` на CPU (ONNX) |

### Воспроизводимость

Повторный запуск на тех же данных даёт побитово тот же результат — это
проверяется тестом. Обеспечивается тремя вещами: все измерения
детерминированы (медианы вместо оптимизации, фиксированный порядок обхода
файлов), модели сохранены на диск, а вычисления идут в один поток — BLAS
(`OMP_NUM_THREADS=1`) и onnxruntime (`intra_op_num_threads = 1`):
многопоточная редукция складывает числа в недетерминированном порядке.
Параллелизм при необходимости берётся процессами на уровне исследований.
Обучение сети тоже детерминировано: сиды и детерминированные алгоритмы cuDNN.

### Что модель забирает себе, а что нет

Вердикт она берёт там, где есть сквозная метрика «геометрия по предсказанным
точкам против геометрии по разметке эксперта», out-of-fold
(`runs/keypoints/metrics_end_to_end.csv`):

| величина | n | медиана | p90 | порог ТЗ | вердикт |
|---|---:|---|---|---|---|
| угол оси позвоночника | 91 | 0.50° | 1.52° | 5° | да |
| отступ ROI сверху | 150 | 0.43 мм | 1.17 мм | 30 мм | да |
| отступ ROI снизу | 148 | 0.40 мм | 1.23 мм | 30 мм | да |
| отступ ROI латерально | 150 | 0.49 мм | 1.42 мм | 20 мм | да |
| выступ малого вертела | 136 | 0.63 мм | 1.73 мм | разрыв классов ≈2.1 мм | **нет** |

Ротация остаётся за `hip_rotation`: требование ТЗ здесь ≈0.5 мм на точку, а
ошибка самого выступа 0.63 мм при p90 1.73 — сопоставимо с разрывом между
классами. Выступ по разметке лежит в 2.5–10.6 мм (5–95 %), и ошибка в
полтора-два миллиметра на хвосте переводит кадр через границу коридора.
Выступ по точкам пишется в детали как диагностика.

Укладка позвоночника тоже остаётся за `spine_qc`, хотя формально критерий —
«видны верхние края подвздошных костей», и каналы `iliac_right/left` с
калиброванным порогом видимости у модели есть. На 5-фолдовом OOF эксперт
отметил отсутствие гребня в 6 и 5 кадрах, и модель узнала отсутствие в
**одном** из одиннадцати случаев: она дорисовывает гребень, которого нет.
Для критерия, где пропуск нарушения — это ложное «гребни видны», такая
голова видимости непригодна. Видимость идёт в диагностику.

Артефактов модель не ищет: канала под посторонние предметы в ней нет и не
планировалось (это отдельная задача и отдельная модель, см. `TODO.md`).

### Почему она выключена по умолчанию

Три прогона сервиса на одних и тех же 252 кадрах и метках эксперта, меняется
только измеритель угла оси и отступов ROI. Сравнение сделано до подключения
сети `cnn_qc` и правила длины поля, вердикт ROI здесь — по рисунку 6. Сеть не
трогает ни ось, ни отступы, а при правиле длины поля вердикт ROI от измерителя
отступов не зависит вовсе, так что вывод тот же:

| | контур | точки, out-of-fold | точки, ансамбль 5 фолдов |
|---|---|---|---|
| `spine_axis` F1 / ROC-AUC / PR-AUC | **0.44** / **0.82** / 0.32 | 0.30 / 0.74 / 0.24 | 0.34 / 0.80 / 0.34 |
| `hip_roi` F1 / ROC-AUC / PR-AUC | 0.35 / 0.89 / 0.44 | 0.35 / 0.89 / 0.50 | 0.33 / 0.92 / 0.53 |
| macro-F1 по типам | **0.565** | 0.535 | 0.542 |
| время на кадр, медиана (CPU) | **31 мс** | 301 мс | 1303 мс |

Честная колонка — средняя: каждый кадр считает модель того фолда, который его
в обучении не видел (`python -m service.evaluate --keypoints-oof`). Ансамбль
на этих кадрах оценивается на собственных обучающих данных — каждый кадр
видели с разметкой точек четыре модели из пяти, — и выглядит чуть лучше
ровно поэтому.

У контура своя поправка: его пороги подобраны на этой же выборке (порог оси
3.99° вместо 5° из ТЗ), а у точек порог 5° взят из ТЗ как есть. Если сравнивать
out-of-fold с out-of-fold, по оси F1 у контура 0.25 (порог подбирается на
обучающих фолдах, см. выше), у точек — 0.30. По ранжированию (ROC-AUC) контур
лучше и так: 0.82 против 0.74.

Направление расхождения видно в измерениях. На 98 кадрах позвоночника модель
читает угол в среднем на 0.70° больше контура (p90 расхождения 3.42°), причём
**две её конструкции — по центрам тел и по боковым краям — согласны между
собой с медианой 0.45°**: модель уверенно расходится с контуром, а не шумит.
На 10 кадрах, где эксперт отметил нарушение оси, медиана угла у точек 4.14°,
у контура 4.02° — обе ниже порога ТЗ, то есть эксперт видит нарушение там,
где обе конструкции меряют меньше 5°. На 88 нормальных кадрах точки дают 12
срабатываний (> 5°), контур — 10 (> 3.99°). Десяти положительных примеров не
хватает, чтобы сказать, какая конструкция ближе к той, что чертит эксперт.

### Отступы ROI: оба метода меряют по рисунку 6

С ответом организаторов (27.09.2026) определение отступов закрыто: как на
рисунке 6 ТЗ, снизу — от нижней точки седалищной кости. Контурный `hip_roi`
перешёл на это определение, и методы сошлись. На 150 кадрах бедра
(out-of-fold):

| отступ | медиана разницы точки−контур | \|разница\| p90 |
|---|---|---|
| сверху | −0.7 мм | 1.6 мм |
| латерально | −1.1 мм | 1.9 мм |
| снизу | −0.9 мм | 2.7 мм |

Ниже 30 мм снизу у обоих методов оказываются по 10 кадров, F1 по ROI у обоих
0.35, ROC-AUC 0.89. Для отступов модель точек ничего не добавляет к контуру:
определение одно, измерение сходится в пределах пары миллиметров, а
расхождения с эталоном у обоих одни и те же — это расхождения эталона с
рисунком 6 (см. `DATASET.md`).

До ответа организаторов контур ставил низ на уровне малого вертела (якорь
«верхушка вертела + 50 мм»), и разница снизу была −19.9 мм при флаге
расхождения на 145 кадрах из 150.

### Расхождение методов не прячется

Когда точки берут вердикт, контурный замер остаётся в деталях (`axis_contour`,
`hip_roi_contour`), а при расхождении больше 2° или 5 мм строка помечается
флагом `axis:keypoints_vs_contour_disagree` /
`roi:keypoints_vs_contour_disagree`. На бедре он срабатывает на 7 кадрах из
150.

**Что нужно, чтобы включить по умолчанию.** В имеющемся наборе размечено
всё, что годится для обучения, фолды обучены все, а по отступам ROI модель
уже совпадает с контуром. Упирается в ось: нумерацию позвонков (учить
четвёрку подряд, а не L1–L4 — уйдут ошибки уровня) и больше положительных
примеров нарушения оси, чем десять, чтобы выбрать между двумя конструкциями
угла.

## Известные ошибки и как они обрабатываются

Необработанных исключений наружу не выходит (ТЗ 2.7): любая ошибка становится
строкой отчёта со статусом `Failure`, текстом в `error` и `quality_class = 1` —
непрочитанный кадр не считается качественным.

| ситуация | поведение |
|---|---|
| битый или не-DICOM файл | строка `Failure`, пачка продолжается |
| сжатый DICOM (RLE, JPEG, JPEG-LS, JPEG 2000) | читается штатно, пиксели совпадают с несжатым |
| DICOMDIR, SR/PDF-отчёты, `.DS_Store`, `__MACOSX/` рядом со снимками | не снимки — строк не дают; DICOMDIR в корне не склеивает выгрузку в одно исследование |
| пустая папка исследования | строка `Failure` с пояснением |
| кадр не похож на DXA | `anatomical_region = unknown`, `violation_type = undetermined`, уходит на ручной разбор |
| перевёрнутый кадр | ловится проверкой ориентации в `region_clf` (100% на суррогатах) |
| зеркальная выгрузка, `PatientOrientation = R\F` | кадр отражается к стандартному виду, сторона бедра определяется верно (тест), флаг `orientation:mirrored_lr` |
| эндопротез | область определяется верно, критерии считаются; эксперт такие бёдра не оценивал |
| нетипичный размер, нули, константа, шум | конвейер отрабатывает без исключений (тест) |
| path traversal в zip | распаковка отклоняется |
| седалищная кость не найдена по кадру (полутоновые кадры) | повтор по строгой маске (`I:strict_mask`), иначе анатомический запас «вертел + 69 мм» (`I:anatomical_prior`) — отступ снизу читать как «не уверены»; на вердикт по длине поля (по умолчанию) не влияет |
| сколиоз | флаг `axis:curved`; эксперт сколиоз нарушением оси не считает, а сервис по углу может поставить `spine_axis` — главный источник лишних срабатываний оси |
| расхождение двух оценок критерия | флаг `*:estimates_disagree`, уверенность low |
| сеть и геометрия расходятся (ротация, предметы) | вердикт по своду, флаг `*:cnn_vs_geometry_disagree`, уверенность low |
| нет onnxruntime или весов сети | кадр считается геометрией, флаг `cnn:unavailable(...)` — сервис не падает |
| снимок 12 или 16 бит | для сети яркость нормализуется по перцентилям 0.5–99.5, геометрия работает в своих единицах |

Флаги едут в колонке `flags` и в JSON измерений.

## Ограничения

- **Один аппарат.** Все 100 исследований сняты на GE Lunar Prodigy Advance.
  Масштаб 0.600 мм/px для позвоночника и 0.607 для бедра задан константой,
  потому что `PixelSpacing` пуст, а `ExposedArea` ненадёжен. На другом
  денситометре константу надо перепроверить, а модели переобучить — это минута.
- **Нанесённая оператором разметка не проверяется**: её нет в данных — ни
  ROI, ни линий, ни оверлеев. По ответу организаторов других критериев сверх
  ТЗ нет, а эталон — `разметка.xlsx`; корректность разметки в нём — это
  столбец «корректность области интересов» бедра, то есть отступы поля
  сканирования, их сервис и проверяет. Все пять критериев оцениваются по
  самому изображению.
- **ROI бедра — как эксперт, а не буквально по рисунку 6.** Эталон
  (`разметка.xlsx`) с рисунком 6 не согласуется на 14 кадрах: снизу — «норма»
  при 1.7–3.0 см под седалищной костью, сбоку — «норма» при 1.6–1.8 см и
  «нарушение» при 2.1 см. Эксперт судит по длине поля, и сервис по умолчанию
  делает так же (F1 0.71 против 0.35). Отступы по рисунку 6 показываются в
  отчёте и интерфейсе, режим строго по ТЗ — `--roi-rule margins`: какое
  определение считать эталонным, решают организаторы, переключение — одним
  флагом без переобучения. Расхождения перечислены в `DATASET.md`, эталон не
  правится.
- **Ось и сколиоз.** Эксперт не ставит нарушение оси при сколиозе (14 кадров
  из 14), сервис по углу — может; отличить сколиоз от наклона по поясничному
  отделу не удалось. Нужна разметка сколиоза или снимки грудного отдела.
- **Верхняя граница укладки (половина тела Th12) не проверяется.** Разметки
  уровня Th12 в данных нет, проверять правило не на чем. Запас кадра сверху
  считается и кладётся в отчёт как диагностика, но в вердикт не входит.
- **Ротация бедра** — самый трудный критерий: ROC-AUC свода 0.82, но F1
  out-of-fold 0.55. При расхождении сети и выступа кадр помечается флагом.
- **Сеть обучена на одном аппарате и 99–150 снимках.** На другом денситометре
  её нужно дообучить тем же скриптом (`python -m cnn_qc.train`); яркость для
  сети нормализуется по перцентилям, так что 12-битный вход её не сломает, но
  другой вид снимка — может. Тепловая карта сети грубая (10 × 10 на кадр): она
  показывает область, а не точку.
- **Статистики нет.** 3–36 положительных примеров на критерий; доверительные
  интервалы широкие, и это видно в таблицах. Разницу между вариантами
  алгоритма в пределах интервала считать значимой нельзя.
- **Фильтр чужих кадров проверен на суррогатах** (искажениях своих же кадров),
  а не на настоящих снимках предплечья или whole body — их в наборе нет.
- **Модель ключевых точек по умолчанию выключена.** Обучена на всех 242
  размеченных кадрах, 5 фолдов; подключается флагом `--keypoints`. Честное
  out-of-fold сравнение проигрывает контурной геометрии: macro-F1 0.535 против
  0.565 (прогон без сети `cnn_qc`), время на кадр 301 мс против 31. Разбор — в
  разделе «Модель ключевых точек».
