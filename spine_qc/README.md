# Критерии качества кадра поясничного отдела: `spine_qc`

Три критерия из ТЗ (п. 2.3, пункт 1) по одному снимку позвоночника: укладка,
наклон оси, посторонние предметы.

## Использование

```bash
python -m spine_qc.predict снимок.dcm
python -m spine_qc.predict папка --csv out.csv
python -m spine_qc.predict снимок.dcm --json --overlay out.png

python -m spine_qc.calibrate --sweep     # пороги, модель, OOF-метрики
```

```python
from spine_qc import SpineQC
qc = SpineQC()
res = qc.analyze('снимок.dcm')
res['quality_class']                      # 0 / 1
res['violations']                         # ['ось позвоночника отклонена на 6.6° (допустимо 5°)']
res['criteria']['axis']['angle_deg']      # -6.58
res['criteria']['position']['iliac_area'] # 0.0
res['flags']                              # ['axis:curved']
```

Без `model.joblib` и `thresholds.json` модуль работает на одной геометрии и
порогах по умолчанию, помечая это флагом `*:no_appearance_model`: сервис должен
подниматься, даже если веса не подложены.

## Место в конвейере

После `region_clf` (кадр принят, метка `spine`). На вход — только пиксели: ни
тегов, ни имён файлов, ни соседних кадров. Разбор кадра делается один раз
(`geometry.spine_column`) и переиспользуется всеми тремя критериями.

## Как считается

**Колонна позвоночника.** Маска кости (гистерезисный порог, трёхклассовый Оцу —
из `hip_roi.geometry`, примитивы там не специфичны для бедра), коридор по
костной массе, затем для каждой строки левый и правый край и взвешенный по
яркости центр тела.

Центр берётся **внутри костного отрезка**, содержащего коридор, а не по окну
фиксированной ширины вокруг него. Это не деталь: взвешенный центр по окну
утягивают рёбра, гребни подвздошных костей и яркие мягкие ткани, трек уходит
с позвоночника, и AUC оси падает с 0.83 до **0.57**. Строки, где отрезок
заметно шире или уже типичного (таз, крестец, разрыв маски), в оценку не идут.

| критерий | измерение | вердикт |
|---|---|---|
| ось | прямая Тейла-Сена по центрам тел, угол к вертикали | \|угол\| > 4.0° |
| укладка | доля костных пикселей в нижних латеральных зонах | < 0.001 |
| артефакты | white top-hat: длина × вытянутость × контраст ведущей структуры | > 24.0 |

**Ось.** Медиана попарных наклонов, а не МНК: одна строка, где маска слилась с
ребром, смещает МНК на градус, медиану — нет. Порог 4.0°, а не 5° из ТЗ:
оценщик читает примерно на градус ниже конструкции эксперта (медиана на
нарушениях 4.0°). Измеренный угол идёт в отчёт как есть. Изгиб больше 12 мм →
флаг `axis:curved` (сколиоз: ось вертикальна, позвоночник изогнут).

**Укладка.** У всех 6 помеченных экспертом кадров костной массы в нижних
латеральных зонах нет вовсе (0.000) против медианы 0.086 у нормы — гребни
подвздошных костей просто не попали в поле сканирования.

**Артефакты.** Структурный элемент top-hat шире косточки белья (2–4 px) и уже
тела позвонка, поэтому металл остаётся, а кость и мягкие ткани уходят в фон.
Яркостью металл не берётся: экспорт Lunar уже насыщен, `max = 255` на всех 99
кадрах, кортикальная кость такая же белая. Колонна из зоны поиска исключается —
её собственная текстура даёт такой же отклик.

## Две оценки и сверка

Каждый критерий измеряется дважды, расхождение идёт во флаг
`*:estimates_disagree`. Вердикт выносит геометрия, вторая оценка задаёт
уверенность.

| критерий | оценка B | OOF AUC оценки B | корр. рангов с A |
|---|---|---|---|
| ось | угол по боковым краям колонны | 0.798 | 0.59 |
| укладка | вид кадра целиком (лог. регрессия) | 0.729 | 0.63 |
| артефакты | вид кадра целиком | 0.646 | 0.16 |

Независимость проверена, а не предположена. Регрессия, обученная на тех же
четырёх морфологических признаках, что складывает счёт артефактов, расходилась
с ним на **1 кадре из 99** — такая сверка не проверяет ничего. Замена на «вид
кадра целиком» дала 32 расхождения, и они осмысленны: где обе оценки согласны,
специфичность 0.99. Для оси вид кадра оказался бесполезен (AUC 0.57), поэтому
там вторая оценка — другая геометрическая конструкция угла; на кадрах, где обе
сходятся в пределах 2°, F1 критерия 0.50 против 0.41 на всех кадрах.

## Результаты

Out-of-fold: порог и модель учились только на обучающих фолдах, метрика — на
отложенном (5 фолдов, группировка по исследованию).

| критерий | + | чувств. | специф. | F1 | AUC измерения |
|---|---:|---|---|---|---|
| укладка | 6 | 0.67 | 0.84 | 0.32 | 0.823 |
| ось | 10 | 0.30 | 0.88 | 0.25 | 0.824 |
| артефакты | 17 | 0.53 | 0.94 | 0.58 | 0.794 |

AUC измерений устойчив (0.79–0.82), неустойчива отсечка: при 6 положительных
примерах на 5 фолдов это один пример на фолд. На всей выборке те же критерии
дают F1 0.91 / 0.44 / 0.65 — разница и есть цена подбора порога.

### Почему вердикт выносит геометрия

Выбор правила свёртки проверялся по OOF (`--sweep`). По метрикам на всей
выборке лучшим для укладки казалось согласие обеих оценок (F1 0.73), но
out-of-fold оно ловит 1 нарушение из 6 (F1 0.29). Сверх метрики: вердикт
геометрии оператор проверяет глазами за секунду («гребни не визуализированы»),
вердикт модели по виду кадра — нет.

## Ограничения

- **Верхняя граница укладки (половина тела Th12) не проверяется.** Разметки
  уровня Th12 в данных нет, проверять правило не на чем. Запас кадра сверху
  (`top_margin_mm`) считается и идёт в отчёт как диагностика.
- **Сколиоз, перелом, люмбализация** — клинические особенности, а не ошибки
  укладки. Эксперт пометил их комментарием; критерии ТЗ их не описывают,
  поэтому изгиб выносится флагом, а не нарушением. Часть пропусков оси
  приходится именно на такие кадры.
- Масштаб 0.600 мм/px задан константой (`PixelSpacing` пуст; по `ExposedArea`
  на 74 согласованных кадрах медиана 0.600 по ширине, 0.606 по высоте).
- 6, 10 и 17 положительных примеров — статистики нет, интервалы широкие.
